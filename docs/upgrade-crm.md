# Обновление 0.2.0 → 0.3.0

Активный каталог пилота после подтверждённой установки 0.2.0:
`/opt/center-messenger-accounts-39065904111`. Исходный foundation-каталог
`/opt/center-messenger` сохраняется для истории, но не является текущей версией.

Использовать только пакет `center-messenger-linux-amd64` из указанного успешного
CI, проверить внешнюю SHA-256, распаковать в новый отдельный каталог и запустить
его `python3 scripts/load_image.py`. В release.json должны быть stage
`crm_connections`, точный commit сборки и прежний digest PostgreSQL. Порядок
скачивания аналогичен upgrade-accounts.md; старые пути нельзя переносить буквально.

## До миграции

1. Из **активного каталога 0.2.0** создать новую `pg_dump -Fc` копию и прочитать
   её оглавление `pg_restore --list`. Сохранить `.env`, `.secrets`, Compose и release.json
   в отдельной папке 0700, dump 0600. Копия до установки 0.2.0 не содержит
   впоследствии созданный аккаунт владельца и не заменяет свежую копию.
2. Сравнить digest PostgreSQL нового и действующего пакетов. В этом обновлении
   контейнер БД не заменяется. Проект и том прежние: `center-messenger`,
   `center-messenger_database`.
3. В новом каталоге скопировать `.secrets` из активного 0.2.0 без замены `.env`:
   новая `.env` должна сохранить тег нового образа. Выполнить `scripts/init_secrets.py`;
   действующие пароли и bootstrap-code сохраняются.
4. Выполнить `python3 scripts/init_connector_key.py`. По умолчанию создаётся
   `/opt/center-messenger-keys/connection_master_key` вне каталогов релизов и
   резервных копий базы. Каталог 0700, файл 0444, в API монтируется один read-only
   secret. Имеющийся ключ не заменяется. Требуются права создания этого каталога.
   Альтернативный путь задаётся `CM_KEY_DIR` одинаково для скрипта и Compose.
5. Проверить `docker compose config --quiet`.

Ключ шифрования нужно резервировать отдельно, в зашифрованном виде вне VPS.
Не помещать его в ту же открытую копию, что и дамп БД. Без прежнего ключа уже
сохранённые credentials восстановить нельзя: потребуется повторный ввод ключей
API или отдельная процедура ротации. Автоматической ротации этого этапа нет.
Содержимое ключа не выводить в переписку/CI-логи.

## Применение из нового каталога

```bash
docker compose run --rm --no-deps migrate
docker compose up -d --no-deps --wait api
curl --fail --silent --show-error --max-time 15 http://127.0.0.1:8100/health/ready
curl --fail --silent --show-error --max-time 15 https://messenger.rastudio.org/api/system/info
```

Ожидается ready, версия `0.3.0`, stage `crm_connections`. Проверить сайт студии
и повторный вход существующего владельца. Обновление не сбрасывает пароль и не
создаёт нового владельца. Между миграцией и заменой API readiness старого образа
временно будет 503 из-за версии схемы.

Войти, открыть «Подключения», ввести адрес CRM, email API-пользователя и v2api-key.
Нажать «Сохранить и подключить», сверить названия/количество филиалов с CRM,
перезагрузить страницу и убедиться, что список виден из базы. Не присылать ключи
или токены в чат. Если есть ошибка — сообщить её текст без секретов.

Клиентские карточки и переписка в этом этапе не импортируются. До их загрузки
нужны внешние резервные копии и восстановление на отдельной среде. Проверка TOC
не является restore-тестом и не подтверждает заявленные в ТЗ RPO/RTO.

## Откат

Старый образ 0.2.0 требует схемы 0002. Переход вниз с 0003 удалит настройки CRM,
кэш филиалов и аренды; существующие аккаунты остаются. После ввода credentials
такой откат означает потерю настроек и требует отдельного решения. Автоматического
downgrade или удаления томов нет. Прежний ключ хранилища сохранить для резервных
копий. Файлы сайта, PM2 и Nginx не изменяются.
