# Кеш карточек клиентов и быстрый список диалогов

Карточки хранятся в `alfa_family_details`, а задания обновления — в существующей
таблице `outbox_events`, topic `crm.card.refresh`. Это PostgreSQL в постоянном
томе `database`, не память браузера и не временный каталог контейнера. Обновление
API не удаляет факты, задания или сообщения. Миграция схемы не требуется; версия
остаётся `0012_member_sections`.

## Правила загрузки

- Серверный `FamilyCacheWorker` каждые 10 секунд проверяет просроченные источники
  семей с `conversations.needs_reply=true`. Отсчёт 30 минут идёт от последнего
  успешного получения карточки; новые сообщения его не перезапускают.
- Открытие/прочтение переписки не означает ответа. После ответа или явной
  обработки всех связанных диалогов периодическое обновление семьи прекращается.
  Уже сохранённая карточка остаётся в базе.
- Для клиента без неотвеченных сообщений выбор переписки не загружает карточку.
  Закреплённая панель предлагает «Открыть карточку клиента». Эта кнопка читает
  готовые факты и при необходимости ставит серверное задание.
- Готовая карточка и история читаются параллельно. Переключение ребёнка не
  запускает отдельный запрос в CRM. Пустой кеш обозначается как подготовка;
  отсутствие сведений не превращается в нулевой баланс или отсутствие занятий.
- `GET /chats/{id}/family?cached_only=true` только читает сохранённые сведения.
  Обычный GET означает явное открытие; `auto=true` допускается только для
  диалога с неотвеченными сообщениями. Принудительное обновление администратора
  через `POST /chats/{id}/family/refresh` также выполняется сервером.

## Надёжность и нагрузка

Ключ задания: организация, подключение CRM, филиал и AlfaCRM Customer ID. Имена
не используются как идентификаторы. Параллельные открытия объединяются;
`FOR UPDATE SKIP LOCKED` и аренда на 90 секунд защищают обработку. После
перезапуска истёкшая аренда подхватывается другим процессом. Перед публикацией
повторно проверяются владелец аренды, версия настроек и актуальная связь клиента.
Карточка записывается атомарно после получения всех её частей.

Сбой оставляет последнюю удачную карточку. Повторы используют задержку до
30 минут; занятый общий лимит CRM — короткий повтор без сброса прогресса.
Задания и успешные данные не зависят от сессии администратора. В приложении
должен быть включён существующий `crm_sync_worker` (на рабочем сервере он уже
используется для синхронизации CRM).

Используется общий ограничитель запросов CRM. Справочник тарифов переиспользуется
30 минут по подключению, версии настроек и филиалу; финансовые данные клиента
читаются заново. Для большой очереди или медленной CRM фактическое обновление
может опоздать: интерфейс показывает время последнего успеха, подготовку,
просрочку и ошибку. Интервал 30 минут — срок постановки обновления, а не обещание
обойти ограничения внешнего API.

## Список диалогов

Первая порция — 90 лёгких строк. Следующая запрашивается за 2,5 экрана до конца
списка. Запросы прокрутки и опроса не перекрываются. Сервер выбирает точный
упорядоченный префикс одним снимком БД и возвращает новые/изменённые строки и
список ID в текущем порядке. Перемещение диалога между позициями не оставляет
дыр и дублей; неизвестный или истёкший курсор вызывает полный безопасный снимок.
Курсор связан с организацией, пользователем, фильтрами и правом записи; каждый
запрос повторно проверяет доступ. В памяти хранятся не более 64 снимков на
процесс с TTL 5 минут. Данные карточек от этих снимков не зависят.

Факты общей политики очереди сохраняются в той же транзакции, что и сообщение,
с topic `chat.list.state`. Сервер больше не пересчитывает всю переписку каждой
видимой строки при каждом опросе. Старые факты восстанавливаются небольшими
порциями; до готовности действует прежний живой расчёт. Порядок остаётся прежним:
неотвеченные первыми, затем остальные; внутри — от новых к старым, без повышения
приоритета системными уведомлениями. Клиент переиспользует строки DOM и сохраняет
видимую позицию. Строки вне экрана используют `content-visibility: auto`.

## Проверка и установка

Автоматические проверки покрывают обновление, истечение аренды, ошибки CRM,
смену настроек, явное открытие прочитанного клиента, точность сортировки,
подгрузку и смену выбранного клиента. Дополнительные локальные проверки:

```bash
npm test
npm run test:scroll
npm run test:chat-list
npm run test:cabinet
```

`check_chat_list.cjs` использует 1000 вымышленных клиентов и проверяет передачу
только изменённых строк, отсутствие дублей и сохранение положения прокрутки.
`benchmark_chat_queue.py` работает только с изолированной локальной тестовой БД,
создавая 3741 диалог и 52374 сообщения. Рабочая CRM в проверках не используется.

Установка выполняется существующим `ramessenger-local-build.service`: сборка,
проверенный резервный дамп и замена только API. После установки сверить тег
контейнера с текущим SHA main и обновить страницу. Начальное заполнение кеша
выполняется в фоне; до его завершения карточки честно показывают подготовку.
