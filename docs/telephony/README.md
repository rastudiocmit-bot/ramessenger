# Телефония Новофона

Первый выпуск включает разговор прямо в мессенджере через микрофон компьютера
и телефона, входящие, исходящие, историю, аудиоплеер и расшифровку нашим ИИ.
Обратный вызов на отдельное устройство не заменяет встроенный телефон.
Звонки связываются с карточками по внешнему номеру; один звонок и одна
обработка сохраняются независимо от числа связанных учеников.

## Подключение через сайт

В разделе **Подключения → Новофон** владелец или администратор центра вводит
**ключ API сотрудника** и нажимает **Сохранить и проверить**. Отдельное поле
**«Секрет из поддержки Новофона»** хранит второй выданный реквизит. Пустые
поля оставляют соответствующие сохранённые значения без изменения. Назначение
реквизита из поддержки в протоколе ещё не подтверждено: он сохраняется, но
проверка Data API использует только ключ сотрудника в `access_token`.
Это явно обозначено под полем; сохранение секрета не означает его проверку.
Отдельный файл с API-ключом на сервере для этого способа не нужен. Период выборки предзаполнен: 24 часа;
его можно изменить на 3 или 7 дней. Период ограничивает диагностическую
выборку и не задаёт частоту будущего импорта звонков.

В актуальном кабинете ключ сотрудника расположен в «Настройки → Сотрудники
→ сотрудник → Дополнительные настройки → Использование API». Отдельной
вкладки API в этом варианте интерфейса нет. Требуются включённые Data API,
Call API, использование ключа, активность ключа и сохранённые изменения.

Перед проверкой в Новофоне нужно разрешить исходящий IP сервера и права
чтения аккаунта, журнала звонков и линий. Введённый ключ шифруется существующим
серверным хранилищем, с отдельным назначением `novofon` и привязкой к центру
и подключению. Ключ не возвращается в браузер, отчёт или аудит. Пустое поле
при повторном сохранении оставляет ключ; отдельное отключение удаляет оба реквизита.
Профиль оператора и другая организация не могут читать или менять настройки.
Одновременные изменения проверяются по версии; устаревшая проверка не может
восстановить заменённый или удалённый ключ.

Кнопки **Проверить API** и **Проверить доступ к записи** выполняют только
ограниченные чтения. Сетевые запросы идут вне транзакции БД и не используют
браузер, аренды или очередь MAX. Есть лимит проверок и отдельная аренда
проверки подключения. Страница показывает отдельно аккаунт, журнал, линии
и доступ к фрагменту записи. Она не сохраняет список звонков и не создаёт
сообщения в чате. Зелёный статус API не означает готовность браузерных звонков,
полного аудиоплеера или расшифровки; их готовность указана отдельно.

Настройки хранятся в отдельной таблице `novofon_settings`, с FORCE RLS для
центра и администратора. Первоначальная установка этой таблицы потребовала
парного обновления ревизии API/MAX; последующее добавление второго реквизита
использует прежнее зашифрованное поле и не требует миграции. Порядок первой
установки описан в [инструкции выпуска](../operations/novofon-settings-release.md).
Авторизация, адресаты, история и отправка MAX в этом изменении не переписаны.

## Диагностика из checkout

В репозитории добавлена независимая диагностика `scripts/diagnose_novofon.py`.
Она использует только Python 3.11+ и стандартную библиотеку. Не подключается
к PostgreSQL, AlfaCRM, MAX или ИИ, не меняет настройки и не инициирует вызовы.

Проверяет текущую платформу Data API: `get.account`, часовой пояс,
одну страницу `get.calls_report` и одну страницу `get.sip_lines`.
Окно по умолчанию 24 часа, размер страницы 30; максимум 7 дней и 100 строк.
Проверки не являются полным импортом истории. Квоты из metadata учитываются;
при исчерпании новые запросы не отправляются. Автоматических повторов нет.

Для необязательной диагностики из командной строки ключ можно поместить **на сервере** в отдельный файл
`/opt/center-messenger-github/.secrets/novofon_access_token`, с правами `0600`
или `0400`. Не передавать ключ аргументом команды и не присылать в чат.
Добавить исходящий IP сервера в разрешённые IP API Новофона и выдать права
на чтение отчётов и линий. Использовать отдельный ключ с минимальными правами.

Из проверенного checkout:

```bash
python3 scripts/diagnose_novofon.py --token-file /opt/center-messenger-github/.secrets/novofon_access_token
```

По отдельному явному флагу читается не более 64 КиБ первой найденной записи:

```bash
python3 scripts/diagnose_novofon.py --token-file /opt/center-messenger-github/.secrets/novofon_access_token --probe-recording
```

Доступны только HTTPS ссылки на `app.novofon.ru` и `media.novofon.ru`,
с проверкой публичных DNS адресов и каждого перенаправления. API ключ
никогда не отправляется на медиасервер. Прокси окружения отключены.
Префикс записи остаётся в оперативной памяти, на диск не сохраняется.
HTML входа не принимается за аудио. Если выбранная ссылка не сработала,
это не доказывает отсутствие других поддерживаемых способов доступа.

JSON отчёт не содержит исходных телефонов, имён, ключа, SIP паролей или
ссылок на записи. Теги телефонов пригодны для сравнения внутри одного
запуска; между запусками они меняются. Не публиковать сырые API ответы.
Код завершения `0` означает завершённые диагностические проверки, `2` —
ошибку или недостающий ключ. Ни один код не означает готовность телефонии.

## Приёмка этапа

Диагностика всегда честно указывает `stage1_complete: false`: она не
проверяет полный аудиофайл, ASR, регистрацию браузерного телефона или
двустороннюю речь. Наличие SIP линии не доказывает доступность WebRTC.
До реализации следующих этапов дополнительно необходимо:

1. Подтвердить поддерживаемый способ встраивания в нашу CRM. Уточнить SDK
   или интерфейс WebRTC, а при необходимости отдельный SIP и медиашлюз.
   Не подставлять выдуманный WSS адрес или API старой платформы.
2. На выделенных тестовых номерах проверить исходящий и входящий разговор
   внутри мессенджера. Реальным клиентам для технических тестов не звонить.
3. Проверить Chrome/Edge на компьютере, Android Chrome и iPhone Safari;
   микрофон, гарнитуру, двусторонний звук и завершение с обеих сторон.
   Внешнее приложение, расширение или личный кабинет не заменяют приёмку.
4. Проверить HTTPS, разрешения, NAT/ICE и необходимость STUN/TURN.
   Зафиксировать фоновые ограничения мобильных браузеров; не обещать
   звонки при закрытой странице без отдельного доказанного механизма.
5. Проверить полный доступ к записи, длительность, обе стороны разговора,
   воспроизведение и ASR. Частичная загрузка префикса этого не доказывает.

В официальной инструкции есть браузерный телефон и готовые CRM интеграции,
но универсальный SDK нашей интеграции и мобильный транспорт ещё не
подтверждены. При недостающих правах или возможностях фиксируется блокер,
а не зелёная готовность и не подмена браузерного разговора callback.

## Изоляция и дальнейшее подключение

Первоначальный скрипт диагностики не требовал миграций. Форма на сайте
добавляет только отдельную таблицу настроек и совместимое обновление ревизии
API/MAX; новый рабочий контейнер телефонии, браузер и очереди MAX не добавляются. Для последующих этапов использовать отдельный
адаптер и общий слой событий клиента, а не вставку входящих MAX.
Активные разговоры обслуживаются независимо от очередей импорта и ИИ.
Изменение общей схемы БД потребует отдельного совместимого плана выпуска.

Отдельная публикация CLI-скрипта не требует перезапуска API/MAX. Установка
формы настроек требует штатного контролируемого выпуска; GitHub Actions
не используются.
Диагностику выполнять из проверенного отдельного checkout. Не обходить
серверную защиту и не устанавливать отдельный контроллер деплоя.

## Отказы подключения

Сохраняются безопасные уточняющие коды Новофона (`error.data.mnemonic`),
а не сырой текст/параметры ответа. `ip_not_whitelisted` означает запрет IP,
`forbidden` — запрет операции для пользователя. Числовой `-32003` сам по себе
не различает эти причины и не подтверждает правильность ключа. Если Новофон
возвращает IP запроса, показывается только проверенный публичный IP-литерал.
Исходные ключи, ссылки на записи, `error.data.value` и произвольные параметры
не сохраняются и не показываются. Старый отчёт без mnemonic получает
объяснение по числовому коду; точная причина появится при следующей проверке.

Ошибки JSON-RPC с явно указанным `id: null` разбираются как ошибки провайдера;
для успешных ответов и других id сохраняется строгая проверка request ID.
Ограничитель приложения допускает четыре ручные проверки в минуту, отдельно
от квот Новофона; сообщение теперь объясняет паузу и сохранение ключа.

Проверки: `test_novofon_credentials_errors.py` и `test_novofon_ui.cjs`.
Изменение полей/диагностики не требует миграции, обновления внешней policy
или замены закреплённого MAX worker. Выпуск выполняется обычным deploy owner.

Локальная проверка изменения реквизитов: 262 UI-теста, 53 серверных теста
и 27 проверок guard пройдены. Два прежних PostgreSQL-теста в этом окружении
не запускались; обязательные pinned проверки на сервере остаются включены.
