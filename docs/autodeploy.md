# ВНИМАНИЕ: УСТАРЕВШАЯ СХЕМА АВТОДЕПЛОЯ

**Актуальный исходный репозиторий: `rastudiocmit-bot/ramessenger`, ветка `main`.** Документ ниже описывает прежний контроллер, жёстко связанный с другим репозиторием и веткой. **Не устанавливать и не включать этот контроллер для нового репозитория.** Простая замена имени в документации не перенастраивает проверку коммитов, GitHub Actions, systemd-таймер или доверенные артефакты на VPS. До отдельной миграции и проверки безопасный деплой для текущего репозитория — только вручную, с проверенным артефактом, резервной копией и подтверждённым доступом к VPS. Существующий сайт и работающие службы не затрагивать.

# Автоматическое обновление пилота

Сервер сам читает приватный GitHub, используя уже настроенный `gh` текущего root.
Новый входящий порт, SSH-ключ в GitHub, self-hosted runner и webhook не нужны.
Проверка выполняется systemd каждые две минуты, после окончания предыдущей.
Установщик не меняет Nginx, PM2, сайт студии и контейнер PostgreSQL.

## Что считается релизом

Исторический контроллер принимает только **push** коммита ветки `production` репозитория `capitalbtl-lab/center-messenger`. Все три задания `python`, `container`,
`containerd-import` должны завершиться с `success`. PR, workflow_dispatch,
старый успешный коммит при новом сломанном, незавершённые/пропущенные задания,
чужой репозиторий и откат истории production не принимаются. После первого
автодеплоя разрешено только движение истории вперёд. Последний коммит повторно
не устанавливается. Новую версию выпускают переносом проверенного кода в production;
изменения в feature-ветках не являются выпуском. CI сам не сливает ветки.

Перед выполнением кода проверяются SHA-256 ZIP из GitHub API, внешняя SHA-256 tgz,
структура архивов, внутренние суммы, точный commit/run/attempt, linux/amd64,
исходное и повторно экспортированное содержимое Docker-образа. Манифест релиза
содержит version/schema_revision/deployment_format. Старые пакеты без этих полей
не устанавливаются автоматически. Встроенный проверенный загрузчик используется
вместо запуска скрипта из полученного архива.

Доверие к коду ветки production равно правам обновлять приложение на сервере:
Docker и миграции исполняют этот код. В GitHub следует ограничить запись в эту
ветку владельцами выпуска. Контроллер не создаёт ruleset автоматически; наличие
защиты ветки отдельно не подтверждено. Существующий root `gh` имеет repo-доступ;
в дальнейшем его стоит заменить отдельным токеном чтения только этого репозитория
(Contents: read, Actions: read). Секреты GitHub в конфиг контроллера не копируются.

## Однократное включение

Из полностью успешного согласованного CI скачать **отдельный** artifact
`center-messenger-autodeploy` в новую папку 0700. Проверить `sha256sum -c checksums.sha256`.
Из этой папки выполнить:

```bash
python3 auto_deploy.py install
systemctl start --no-block center-messenger-deploy.service
```

Установщик определяет активную папку по labels единственного работающего API
проекта center-messenger, проверяет целостность его исходного пакета, readiness
и доступ gh к репозиторию. Можно явно передать `install --active-root /opt/...`.
На пилоте сейчас активна `/opt/center-messenger-accounts-39065904111` (0.2.0).
Не брать устаревшую `/opt/center-messenger`, где осталась foundation-версия.
Не завершать параллельно ручную установку 0.3.0 после включения таймера.

Контроллер/конфиг/журнал находятся в `/opt/center-messenger-deploy` (0700).
Статус не содержит ключей, паролей или исходных ответов CRM.
Повторный install не сбрасывает журнал и не заменяет существующую конфигурацию.
Контроллер не обновляет свой собственный код вместе с приложением.

## Обновление уже установленного контроллера

Сам контроллер не обновляется вместе с приложением. Для его обновления скачайте
свежий artifact `center-messenger-autodeploy` из полностью успешного CI в новую
закрытую папку и проверьте `sha256sum -c checksums.sha256`. Затем из этой папки
выполните:

```bash
python3 auto_deploy.py --root /opt/center-messenger-deploy upgrade-controller
systemctl start --no-block center-messenger-deploy.service
```

Команда проверяет контрольные суммы файлов, берёт блокировку деплоя и атомарно
обновляет только код контроллера. Конфиг, журнал состояния, файлы секретов,
systemd-служба и таймер остаются прежними. Вторую команду выполняйте после
сообщения `Controller updated`; она запускает уже установленный контроллер.

## Порядок обновления

1. Проверка свежего production CI, скачивание, проверка и импорт готового образа.
   Повторная проверка ветки после скачивания. На сервере ничего не собирается.
2. Проверка прежнего digest PostgreSQL, доступности старого API, свободного диска.
   Перед скачиванием нужно минимум 4 GiB; перед миграцией минимум 3 GiB + два
   размера текущей базы. Недостаток места оставляет прежнюю версию работающей.
3. Копирование **действующих** трёх файлов `.secrets` в новую папку без изменения
   их содержимого. Новая `.env` сохраняет новый образ. Общий ключ коннекторов
   создаётся/сохраняется в `/opt/center-messenger-keys`, отдельно от копий БД.
4. Межпроцессная блокировка и постоянный журнал защищают от второго деплоя.
   Остановка только API, затем согласованный `pg_dump -Fc` и чтение TOC
   через `pg_restore --list`, копирование прежних секретов/Compose/metadata.
   Копия содержит актуального владельца. Во время этого шага кабинет недоступен.
5. `migrate` и запуск только `api` с `--no-deps --pull never`. БД не пересоздаётся,
   её образ и том не меняются. Проверяются фактическая версия схемы, readiness,
   version/stage приложения. Активная папка меняется только после успеха.
6. Проверка публичного HTTPS записывается в статус (`public_check`). Внешняя
   сетевая ошибка после успешного старта не вызывает восстановления старой базы.

Backup — в `backups`, файлы новых версий — в `releases` внутри папки контроллера.
Автоматического удаления дампов, релизов и Docker-образов пока нет. При нехватке
места обновление останавливается; очистка — отдельная операция с учётом отката.
Это локальные копии перед обновлением, а не внешние регулярные backup/PITR.
Чтение TOC не является полной проверкой восстановления. Ключ шифрования нужно
резервировать отдельно от открытой копии БД, зашифрованно вне VPS.

## Ошибка и остановка

До остановки приложения ошибки загрузки/проверки не затрагивают работающий API.
После начала замены неудача блокирует следующие обновления. Если схема осталась
прежней, контроллер пробует запустить прежний API и записывает результат.
Если схема изменилась или её нельзя проверить, автоматического downgrade/restore
нет: такая операция может удалить новые данные. Нужны разбор текущей схемы,
исправленная версия либо согласованное восстановление копии. Не выполнять
`down --volumes` или глобальную очистку Docker. После обрыва/перезапуска процесса
с незавершённым журналом следующая попытка блокируется, а не начинает всё заново.

```bash
python3 /opt/center-messenger-deploy/auto_deploy.py status
journalctl -u center-messenger-deploy.service -n 60 --no-pager
systemctl is-active center-messenger-deploy.timer
systemctl stop center-messenger-deploy.timer
```

Остановка таймера не прерывает уже выполняющийся сервис. Дождаться его завершения
перед ручными изменениями. `resume` разрешает повтор после ошибки **только если**
контроллер уже восстановил прежний API; сначала устранить причину сбоя.
При изменившейся схеме или обрыве процесса состояние исправляется вручную
после проверки реального API/БД. Публичное API не даёт команд управления деплоем.

## Проверки

Unit-тесты проверяют выбор ветки/CI, provenance/digest/архивы, отказ при нехватке
места/другом PostgreSQL, сохранение секретов, резервную копию до миграции,
повторный запуск и разные исходы ошибки. Дополнительно CI на Docker containerd
реально обновляет запущенный пакет, создаёт читаемый дамп и проверяет сохранение
записи в PostgreSQL, затем воспроизводит отказ запуска API при прежней схеме
и восстановление предыдущего API. Работа настоящего systemd на VPS проверяется
после однократного включения пользователем. Доступ к настоящей AlfaCRM этим не проверяется.

Миграции для автоматического выпуска должны оставаться транзакционными для
PostgreSQL. Миграции с внешними побочными эффектами, autocommit или изменением
кластера требуют отдельного сценария и ручного выпуска. Прежняя версия может
восстанавливаться по номеру схемы только при соблюдении этого условия.
