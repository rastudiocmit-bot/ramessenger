# Размещение первого этапа

Для уже работающего пилота подготовлен [контроллер автоматического обновления](autodeploy.md).
Он требует однократного включения на сервере. Описанные ниже ручные команды
не выполнять параллельно с активным сервисом деплоя.

## Известный снимок сервера

По выводу пользователя от 17.10.2026: `83.222.25.109`, 4 CPU, 5.8 GiB RAM,
available 4.6 GiB, диск 77 GiB / свободно 61 GiB, load 0.31/0.16/0.05.
Активны Nginx и PM2; 80/443/3000 заняты. После установки пользователь подтвердил
Ubuntu 24.04.4, Docker 29.9.1, Compose v5.6.0 и успешный hello-world.
Текущий каталог сайта — `/var/www/rastudio`; проект не размещать
внутри этой папки. Снимок не заменяет измерение пиков.

## Порядок, без автоматической установки

1. Проверить Docker/Compose, порт 8100 и запас ресурсов через `sh scripts/preflight.sh`.
   Скрипт только читает состояние. Установку Docker, если потребуется, согласовать
   отдельным шагом после проверки ОС/сети. Не запускать случайный install-скрипт.
2. Выделить проекту собственный каталог, например `/opt/center-messenger`, и права
   пользователя выкладки. Не копировать файлы поверх сайта.
3. Использовать проверенную ревизию кода и заранее собранный образ.
   Production-сборка на сервере сайта не является штатным способом обновления.
4. Подготовить `.env` из примера и указать `CM_IMAGE` проверенного образа.
   Для первого запуска использовать приватный пакет CI, описанный ниже.
5. Запустить `python3 scripts/init_secrets.py`. Скрипт не заменяет существующие
   пароли и не выводит их. Каталог `.secrets` имеет 0700. Отдельные read-only
   secret-файлы доступны соответствующим контейнерам, в том числе non-root API.
6. Проверить `docker compose config --quiet`, запустить БД, применить миграцию,
   затем запустить API и проверить readiness.
7. После локальной проверки настроить DNS и отдельный HTTPS virtual host в
   существующем Nginx по [инструкции HTTPS](https.md). В `infra/nginx` находятся
   начальный HTTP-пример для ACME и итоговый HTTPS-пример; установка ручная.

Пилот уже запущен: [подтверждённые результаты от 17.10.2026](operations/2026-10-17-pilot.md).
На сервере установлена 0.2.0, вход владельца подтверждён. [Журнал установки кабинета](operations/2026-10-17-accounts.md). Обновление до настроек АльфаCRM 0.3.0 описано в [upgrade-crm.md](upgrade-crm.md). Импорт клиентов и мессенджеры ещё не реализованы.

## Последовательность для уже подготовленного образа

Следующие команды выполняются только из каталога мессенджера с его `.env` и
собственными секретами, после проверки инфраструктуры и релиза:

```bash
docker compose config --quiet
docker compose up -d --wait db
docker compose run --rm migrate
docker compose up -d --wait api
curl --fail --silent --show-error http://127.0.0.1:8100/health/ready
```

Ожидается `{"status":"ready"}`. Процесс без миграций или с ролью владельца
возвращает 503. Публичного кабинета на этом этапе ещё нет.

Изменения Nginx: отдельный файл, проверка `nginx -t` и затем управляемый reload;
существующие virtual hosts сохраняются. Эти действия в CI не выполняются.

## Проверка перед внешним включением

- Сайт студии отвечает как до запуска; задержки и использование RAM сопоставлены.
- Мессенджер не слушает внешний 3000/5432/8100 и не занимает 80/443 напрямую.
- При остановке API сайт работает, при отказе БД readiness 503.
- Секреты и том базы имеют резервное копирование вне сервера.
- Общая авторизация кабинета будет реализована до публикации клиентских API.

## Остановка, обновление и восстановление

`docker compose stop api` останавливает только API этого проекта.
Для полного обслуживания проекта использовать его Compose-файл и проверять
текущий каталог/имя проекта. Глобальные очистки Docker запрещены.
В production не использовать `down --volumes`: это удаляет базу.

На foundation-этапе нет готовой системы backup/PITR, поэтому цели полного ТЗ
RPO 15 минут / RTO 4 часа ещё не подтверждены. До клиентских данных настроить
копирование БД/секретов, внешнее хранение и фактический restore-тест.
При откате образа учитывать совместимость схемы; downgrade может удалить данные.

Теги базовых образов закреплены по версиям семейств, но могут обновляться.
Для production-релиза фиксировать проверенные digest и хранить список образов.

## Получение готового образа без сборки на сервере

Успешный CI сохраняет artifact `center-messenger-linux-amd64` на 7 дней внутри
приватного репозитория. Он содержит архив `.tgz` и внешнюю SHA-256-сумму.
Пакет формируется после unit/integration-проверок, сборки и readiness контейнера.
Он не является публичной публикацией и не выкладывается на сервер автоматически.

Внутри: готовый образ приложения, Compose с проверенным digest PostgreSQL,
уникальный тег приложения, ID образа, стабильный digest конфигурации, commit сборки,
внутренние SHA-256-суммы,
скрипты инициализации и инструкция. CI-пароли и каталог `.secrets` не включаются.
Tar сохраняет права init-скрипта; внешняя упаковка GitHub не меняет их.

Пакет можно получить через GitHub CLI после входа владельца либо скачать
в браузере со страницы успешного запуска Actions и загрузить на сервер.
Авторизационные токены и одноразовые коды в переписку не передаются.
Для CLI нужно явно указать репозиторий, ID проверенного запуска и имя artifact.

После скачивания проверить внешнюю сумму, распаковать пакет в отдельный
новый каталог и выполнить `python3 scripts/load_image.py` с Docker-правами.
Скрипт проверяет внутренние суммы, загружает образ, затем повторно экспортирует
загруженный образ и сравнивает SHA-256 исходных байтов его конфигурации и платформу.
Конфигурация включает команды, окружение и упорядоченные digest содержимого слоёв.
Это сравнение работает и в classic store, и в containerd store Docker 29, где поле
`Id` обозначает разные объекты. Просто сравнивать `docker image inspect .Id` нельзя.
Он не запускает контейнеры и не изменяет Nginx/PM2.
Затем выполняется отдельный шаг генерации местных секретов и запуска.
Первичную установку не выполнять поверх существующего каталога приложения;
обновления требуют сохранения секретов и проверки миграций.

## Проверка пакета, уже импортированного старой версией загрузчика

Если старый загрузчик остановился с `Loaded image does not match the tested image`
на Docker 29/containerd, исходный пакет и его `checksums.sha256` сохраняются.
Проверенный CI artifact `center-messenger-import-fix` содержит отдельный загрузчик
и его SHA-256-сумму. Его скачивают в новый отдельный каталог и после проверки суммы
запускают оттуда с `--bundle-root /opt/center-messenger --verify-only`.
Скрипт сверяет исходные файлы и содержимое уже импортированного образа; контейнеры
не создаются. Исходный загрузчик не заменяется: он также включён в старые суммы.
Для старого пакета ожидаемый config digest берётся из его прежнего classic-store
`image_id`. Если он не совпадает с конфигурацией архива, проверка завершается ошибкой.
После успешной проверки можно продолжить отдельный шаг инициализации базы.
