# Постоянный прокси Grok для всех агентов

Прямые запросы VPS к `/v1/language-models` и `/v1/api-key` возвращали HTTP 403.
01.11.2026 пользователь подтвердил: через его SOCKS5-прокси каталог вернул
HTTP 200 с `grok-4.7` и `grok-4.6`, с проверкой TLS-сертификата. Это проверка
каталога, а не подтверждение успешной платной генерации. Реальные реквизиты
ключа и прокси в репозиторий, команды установки и журналы не включаются.

## Поведение выпуска

Одна настройка Grok применяется к проверке подключения, трём общим назначениям
агентов, тесту телефонного агента и фоновому описанию звонков. Прокси сохраняется
отдельным шифротекстом в существующем `gateway_config.grok`. Схема БД,
зависимости, Compose, хранилище секретов и конфигурация MAX не меняются.

При ошибке прокси прямой маршрут автоматически не включается. Смена активного
маршрута сбрасывает проверку; незавершённое телефонное задание обнаруживает
смену до следующего платного запроса. Сохранение не вызывает генерацию.

## Отдельный серверный допуск

Это защищённое обновление API и телефона. Обычный таймер не имеет права
самостоятельно заменить установленный эталон. Требование AGENTS.md:
«Subsequent guard and baseline updates require explicit server installation».
Работа ведётся в отдельной ветке; до готовности серверного допуска её не надо
переносить в main, блокируя тем самым очередные обычные выпуски.

Предыдущая policy:
`d3e9e52f4b0883e124f1b89c146a1fb7296715709e76dd093e3d002e440ef116`.

Новая policy:
`59d7b7adad59c5fecceb1ca0390126050babdbb16d97e697eb378109f4b1eb34`.

Контракт телефона: `novofon-family-care-grok-proxy-v3`.
Контракт MAX и `worker_runtime_contract` остаются прежними; схема —
`0032_telephony_ai`.

Проверенные изменения защищённого контура:

- `ai_grok.py`: отдельный конверт прокси, сохранение, проверка текущего
  маршрута и передача прокси в запрос клиента; различение HTTP 401/403.
- `ai_gateways.py`, `ai_voice.py`: выбранный прокси передаётся только Grok.
- `telephony_agent.py`, `telephony_ai_worker.py`: тот же маршрут и снимок
  активного подключения для фоновых заданий.
- Общий `grok_proxy_probe.py` теперь входит в эталон: GET по-прежнему разрешены
  по умолчанию, а POST разрешён только явным производственным клиентом и только
  к `https://api.x.ai/v1/responses`. TLS-проверка остаётся обязательной.
- Тесты Grok, телефона и новые тесты транспорта/диагностики входят в закреплённый
  комплект. PostgreSQL-тест проверяет сохранение независимых JSON-настроек.

После проверки актуального main выпуск переносится с сохранением промежуточных
изменений. Для точного итогового SHA через серверную консоль запускается
существующий `scripts/prepare_telephony_update.py`: проверяются SHA живого API,
его image, текущие image MAX/телефона и обе policy. Затем единственный владелец
выкладки `ramessenger-local-build.service` выполняет оба обязательных MAX gate,
резервную копию, обновление телефона и API, readiness и штатный откат при сбое.
Точная команда выдаётся после окончательного SHA main; пароль прокси в неё не входит.

## Проверки и включение

Локально прошли 382 проверки интерфейса, 187 тестов серверного кода/защиты
и Chromium при ширине 1440, 390 и 320 px. Сетевые ответы синтетические.
Локальный MAX offline запуск охватил 425 тестов, но не прошёл: один тест не
нашёл штатный Chromium Playwright, ещё 11 проверок пропущены в ограниченной
среде. Это не успешный gate. Контейнерный database gate и изменённый
PostgreSQL-тест локально не запускались. Оба gate обязательны на сервере до продвижения.

После `LOCAL DEPLOYED` и healthy API/телефона владелец открывает
«Подключения → ИИ-шлюзы → Grok → Прокси для всех агентов Grok», вводит реквизиты,
выбирает SOCKS5 или HTTP CONNECT, включает общий маршрут и сохраняет.
Затем «Проверить подключение» делает один ограниченный платный запрос из
существующего бюджета. Только его успех подтверждает генерацию. Проверка
телефонного профиля использует тот же прокси; ASR настраивается независимо.
