# Защита действующего MAX через AlfaCRM

## Объём и состояние

Первый этап — защита от случайных правок и ошибочного выпуска. Код MAX,
данные, UI и алгоритмы загрузки не переносятся и не переписываются. Новых
сервисов, процессов приложения, API каналов и миграций нет. Краткоживущие
контейнеры ниже используются только для тестов перед выпуском.

Подготовка в репозитории не означает установку на VPS. До установки внешнего
проверяющего модуля старый загрузчик продолжает обычный деплой без этой защиты.
Публикация в `main` при работающем таймере может запустить выпуск: сначала
завершить проверку резервного восстановления, установить guard с рабочим
API без его перезапуска, проверить preview, затем интегрировать выпуск.

Исходная версия приложения: `30ae13c5f03f1009d6b1b63a3ab1a349119bb9ce`;
Docker tag `center-messenger:local-30ae13c5f03f`; схема
`0029_invitation_sections`. Это наблюдавшаяся рабочая версия, а не утверждение,
что ранее были пройдены все приведённые ниже тесты. Реальные сессии, данные
CRM и пароли в эталон не включаются.

и миграции по сравнению с указанной рабочей версией не изменены.

## Почему проверка находится вне main

Старый `local_build_vps.py` выполнял `self_update(sha)` до проверки кода:
скрипт из `main` мог заменить самого проверяющего. Обычный manifest в том же
коммите этого не предотвращает.

Явная установка создаёт `/etc/ramessenger-max-guard/<policy-sha256>/`:
закреплённые policy, runner, promoter, guard и тесты. Файлы принадлежат root,
другие пользователи их не меняют. `active` указывает на конкретное поколение.
Systemd drop-in `50-max-guard.conf` заменяет только `ExecStart` существующего
`ramessenger-local-build.service`; таймер, support-очередь и deploy-lock общие.
Ни резервное копирование, ни ручные скрипты не должны удалять этот drop-in.

Последовательность обычного выпуска:

1. Проверка целостности установленного guard и блокировка `.deploy.lock`.
2. Проверка существующего `enabled`; определение точного SHA `main`.
3. Выгрузка этого SHA без выполнения кода выпуска.
4. Сравнение с установленным эталоном: изменения, удаления, symlink,
   новые миграции и новые модули защищённых имён. Manifest тоже сравнивается
   с внешней копией, поэтому изменить код и переписать хэши недостаточно.
5. При отличиях — блокировка до отдельного серверного допуска. API работает.
6. Закреплённый runner получает именно проверенные каталог и SHA, не меняет
   себя и не загружает другой `main` как цель. Проверка происхождения текущего
   образа, ancestor и отсечение устаревшего выпуска сохраняются.
7. Сборка образа, проверка схемы и совместимости. Тесты берутся из внешней
   копии, приложение — из нового образа. Переписать тесты тем же коммитом
   для получения зелёного результата нельзя.
8. Только после успешных проверок — штатный pg_dump, повторная проверка
   актуальности SHA, миграция при необходимости, API readiness и rollback.

Это защита от ошибок разработки, а не от администратора root, компрометации
хоста или намеренно вредоносного коммита. Root может изменить systemd.
Совместимость общих частей покрыта выбранными тестами, а не математически
доказана. Изменения страниц AlfaCRM требуют отдельной проверки источника.

## Обязательные проверки

Проверка guard — `python3 -m unittest discover -s tests -p test_max_release_guard.py`.
Тестирует изменение/удаление файлов, подмену policy вместе с проверкой,
новую миграцию, точный SHA/срок допуска, неизменяемые тесты, блокировку до
действий с БД/API и сохранение отсечения устаревших сборок.

Перед каждым выпуском две части `tests/run_max_compatibility.py`:

- Offline: разбор истории без пропуска строк, курсоры, выбор точного
  адресата при нескольких карточках, неопределённый результат отправки,
  журналирование результата до экспорта cookies, сетевые ошибки и повторы.
  Контейнер `--network none`, read-only root, без секретов и рабочей БД.
- Database: новая временная PostgreSQL того же image ID в уникальной
  `--internal` сети, с синтетическими учётными данными и tmpfs. Выбранные
  тесты проверяют повтор страницы без дубля, два одинаковых текста как
  разные исходные сообщения, сохранение истории после сбоя/перезапуска,
  автоматическое восстановление сессии, запрет повторного POST при `unknown`,
  устаревшие аренды, смену получателя и параллельный доступ. Применяются
  миграции нового образа в тестовую БД, не в production.

Пропуск обязательного теста, ошибка импорта или пустой suite блокируют выпуск.
Рабочий том PostgreSQL, порт и секреты не подключаются. Удаляются только
тестовые контейнеры/сеть этой проверки; `docker system prune` не используется.
Live CRM тесты не выполняют реальные отправки автоматически. Отдельная
GET-only диагностика источника необходима при изменении формы AlfaCRM.

Локальная среда без Docker или полноценного `/proc` не заменяет эти два
контейнерных теста. В отчёте нужно отличать пройденные unit-тесты от ещё не
выполненной проверки на VPS. Блокировка выпуска не останавливает рабочий API.

## Установка после проверки бэкапа

Выполняет root из отдельного проверенного checkout `ops/max-release-protection-20261030`.
Не запускать из `/tmp` в предположении, что это git-репозиторий. Сначала
проверить полный SHA checkout и SHA-256 `deploy/max-protection.json`; значение
из проверенного отчёта передать явно. Не брать автоматически «последний main».

```bash
python3 scripts/max_release_guard.py install --source "$PWD" --expected-policy <проверенный_SHA256_policy> --expected-live 30ae13c5f03f1009d6b1b63a3ab1a349119bb9ce
python3 /etc/ramessenger-max-guard/active/scripts/max_release_guard.py run --preview
```

Установка выполняется под существующим deploy-lock и не останавливает API.
Первый preview до интеграции файлов защиты в main закономерно покажет их
отсутствие и заблокирует выпуск: это не повод выдавать обходной допуск.
После интеграции этой же проверенной версии preview должен пройти.
Посмотреть фактический entrypoint: `systemctl cat ramessenger-local-build.service`.
Установка сама не запускает сборку, обновление схемы или перезапуск API.

После установки включить в будущие бэкапы весь `/etc/ramessenger-max-guard/`
и `/etc/systemd/system/ramessenger-local-build.service.d/`. Текущий старый
бэкап, созданный до установки, не может содержать эти файлы.

## Контролируемое исправление MAX

1. Отдельная задача/ветка, описание причины и затронутых инвариантов.
2. Не переписывать остальные изменения. Тесты core + общий deploy regression,
   изолированная БД; при изменениях HTML — GET-only диагностика AlfaCRM.
3. Получить отчёт внешней проверки для полного SHA:
   `python3 /etc/ramessenger-max-guard/active/scripts/max_release_guard.py inspect --sha <SHA>`.
4. После предметного просмотра diff root даёт допуск вне репозитория:
   `python3 /etc/ramessenger-max-guard/active/scripts/max_release_guard.py approve --sha <SHA> --expected-diff <diff_sha256_из_отчёта> --reason '<причина и проверка>'`.
   Допуск действует 24 часа только для этого SHA, diff и установленного policy.
   Следующий коммит его не наследует. Его нельзя записать в Git или передать
   переменной окружения. Проверки поведения обязательны и при допуске.
5. Штатный выпуск через единственный service/timer; проверить фактический
   image, readiness и диагностику. Не повторять реальные отправки вслепую.
6. После успешного выпуска подготовить новый manifest отдельным осознанным
   изменением, сверив каждый изменившийся хэш. Никакого автообновления эталона
   на каждом деплое. Для замены внешнего поколения нужны новая проверенная
   policy, `--expected-live <фактический_SHA>` и
   `--previous-policy <SHA256_установленной_policy>` в команде `install`.

Runner/promoter/guard обновляются только такой явной установкой: допуск
изменений в приложении не заставляет сервер выполнить новый runner из Git.
Неизменённые общие файлы не требуют отдельного допуска. После принятого
изменения MAX до обновления эталона следующий SHA снова потребует допуска.

## Следующие каналы — только архитектурное правило

ВКонтакте, Одноклассники, Telegram получат отдельные вкладки и коннекторы,
свои авторизацию, курсор, идемпотентность, адресата и подтверждение отправки.
Не подменять ими `alfa_max_browser` и не расширять его HTML-парсер ради
другого мессенджера.

Общее: CRM-представитель/ученик и явно подтверждённые связи с диалогами.
Сущности различаются: CRM Customer ID + филиал; CRM-контакт/семья;
channel_kind + connection_id + external_peer_id + conversation_id.
Одного телефона недостаточно, чтобы слить разных учеников или адресатов.
Исходные CRM ID, source ID и происхождение записи сохраняются.

Опциональная история конкретного клиента может показывать связанные
диалоги с обозначением канала. По умолчанию глобального объединённого чата
нет. Ответ отправляется в исходный диалог; смена канала — явное действие.
Реализация адаптеров, вкладок, новых таблиц и перенос MAX в отдельный сервис
отложены на следующие этапы.
