# Восстановление привязки клиентов и копий истории

Рабочий отчёт от 24 октября показал 27 диалогов для семи проверенных CRM ID:
семь привязанных диалогов и 20 филиальных диалогов без контакта. Например,
клиент, найденный в справочнике только второго филиала, имел дополнительные
диалоги первого, третьего и четвёртого филиалов. URL просмотра журнала оказался
недостаточным основанием для определения принадлежности клиента филиалу.

В 20 образцах повторов обнаружены две разные ситуации. Входящие журналы
филиалов содержат копии с разными CRM row ID, одинаковыми клиентом, содержимым
и временем. Также сохранены старые записи без `crm_record_id` рядом с новыми
записями. Число 276 в отчёте — кандидаты по тексту и времени, не доказанное
число дублей. Персональные сообщения в репозиторий не перенесены.

## Правила исправления

- Клиент определяется по числовому ID опубликованного справочника AlfaCRM.
  Если все подтверждённые соответствия этого ID указывают на один контакт,
  он используется и при чтении журнала другого филиала. Для ответа выбирается
  доступное подтверждённое членство. Если один ID соответствует разным контактам,
  сохраняется точная привязка филиала, автоматического объединения нет.
- Старые филиальные диалоги с подтверждённым CRM ID присоединяются к каноническому
  контакту. Сохраняются ID старых диалогов как ссылки, сообщения, команды отправки
  и отметки обработки. Открытый старый диалог перенаправляется на канонический.
- Для импорта до появления `crm_record_id` точный числовой ID восстанавливается
  из `crm_order`: исходный импортёр записывал туда числовой ключ строки CRM.
  Копии одного ID внутри одного филиала скрываются по идентичности источника,
  даже если текст впоследствии изменился. Исходная строка и прежний provider ID
  сохраняются. Две разные команды отправки не объединяются автоматически.
- Копии между филиалами учитываются только для входящих, одинаковых подтверждённых
  CRM клиентов, точного времени, содержимого, вложений, типа автора и признака
  ошибки. Отдельные CRM ID источника сохраняются. Сообщения сортируются внутри
  каждого филиала, и сопоставление выполняется по номеру в этой группе. Поэтому
  два одинаковых сообщения в одну минуту в одном журнале остаются двумя.
  При неполной загрузке остаётся максимальная наблюдаемая кратность по филиалам.
  Пока основной экземпляр не получен, доступна копия из другого филиала.
- Разные CRM клиенты и самостоятельные исходящие из разных филиалов не считаются
  такими копиями. Поле `crm_mirror` отделяет копию журнала от удаления сообщения.
  Все оригинальные строки и ссылки источников остаются в базе. Полнота журналов
  считается с учётом сохранённых копий, отображение переписки — без них.
- Если точного исходного ID нет, строка остаётся видимой. Отчёт показывает
  `unidentified_rows`, а история не объявляется полностью проверенной.

## Запуск и наблюдение

Восстановление запускается обработчиком автоматически. Его отдельная позиция
`client_repair` сохраняется после каждых 20 контактов; после трёх порций выполняется
обычное чтение CRM, чтобы восстановление не вытесняло новые сообщения. Перезапуск
продолжает процесс с позиции. Новый опубликованный справочник проверяется заново.
Пустые диалоги для клиентов без сохранённой истории не создаются.

Позиции архивного обхода сохраняются. Повторный полный обход не нужен для
восстановления уже записанной истории. Если восстановленные ID закрыли недостачу
ранее завершённого журнала, ненужный повтор снимается. Плановый шестичасовой
обход поздно добавленных старых записей продолжается.

В подключениях отображается «Восстанавливаем историю клиентов: проверено …».
Отдельно показаны сообщения в переписках и общее число записей в базе. Число
видимых сообщений и диалогов может уменьшиться при сохранении исходных строк.

После установки обновить страницу. Для немедленного запуска обработчика можно
один раз нажать «Синхронизировать историю»; позиция восстановления сохраняется.
Проверка результата без изменения данных:

```sh
docker exec center-messenger-api-1 /opt/venv/bin/python -m center_messenger.history_audit
```

Проверить `client_repair.complete`, `unidentified_rows`, `history_complete`,
`missing_rows` и ошибки отдельных журналов. Публикация кода сама по себе не
подтверждает завершение обработки рабочей базы: прямого доступа к ней из среды
разработки нет.

## Проверки

82 Python-проверки прошли на PGlite с 12 миграциями; один тест конкурентности
обычной PostgreSQL явно пропущен. 32 теста интерфейса прошли в jsdom. Сценарий
из отчёта воспроизведён на вымышленных данных: 32 сохранённые строки для двух
клиентов и четырёх филиалов дают шесть видимых событий, все 24 источника остаются
доступны для сверки. Следующее живое событие даёт одно сообщение вместо четырёх.
Проверены перенаправление диалогов, продолжение порций, отсутствие пустых диалогов,
повторные одинаковые сообщения, несовпадающие CRM контакты и отметки обработки.

Chromium 153: весь кабинет восстанавливает опрос после 503 и таймаута; прокрутка
201 сообщения сохраняет привязку с отклонением 0 пикселей при старой странице
и −0,5 пикселя при смешанном обновлении. Ошибок JavaScript нет.
Миграций схемы, изменений зависимостей или контроллера развёртывания нет.
