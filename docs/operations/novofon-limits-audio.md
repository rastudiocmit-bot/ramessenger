# Квоты Новофона и чтение аудиозаписей

## Подтверждённая ошибка аудио

31.10.2026 на рабочем `eb4cabc9adbf` загружены 33 звонка, у 30 есть
зашифрованные ссылки. Диагностика записи Глазковой вернула 503 от worker:
«Не удалось прочитать ключ API». Импорт сохранял `{url}`, а общий `open()`
требует `{api_key}`. Это ошибка формата в приложении до запроса аудио,
а не подтверждение недоступности записи у провайдера.

Общий валидатор ключей сохранён. Новые `seal_recording/open_recording`
отдельно обрабатывают URL: новый r1-формат AEAD привязан к workspace,
connection и call. URL-only записи прежнего v1-формата читаются без
перезаписи БД. API-ключ не принимается за аудиоссылку. Допустимые HTTPS-хосты,
проверка публичного DNS, ограничения диапазонов и формата звука сохраняются.
Тест проходит через настоящий worker ASGI и настоящий ConnectorVault для
старого и нового формата. Полное воспроизведение на VPS/в браузере проверяется
после выпуска отдельно. ASR в этом выпуске не добавляется.

## Источники ограничений

Проверены официальные документы 31.10.2026:

- https://novofon.github.io/data_api/ — `metadata.limits` в успешных и
  ошибочных ответах, поля day/minute limit/remaining/reset, RPC -32029 и
  mnemonic `limit_exceeded`, pagination limit до 10000 и offset до 100000.
- https://novofon.github.io/call_api/ — лимиты в баллах и reset в секундах.
  Call API имеет собственный endpoint/контракт. Он сейчас не вызывается;
  будущий встроенный телефон должен иметь отдельный бюджет Call API.

Числа 3000/60 из примеров нельзя объявлять тарифом конкретного аккаунта.
Приложение читает фактические пределы и остатки из ответа. Если метаданных
пока нет, действует наш осторожный bootstrap 6 единиц/минуту и 500/сутки,
с одним первоначальным запросом. Это локальная страховка, не лимиты Новофона.
После первого ответа допустима короткая серия до трёх запросов для проверки
подключения; затем темп учитывает и минутный, и суточный остаток до сброса.
Стоимость метода оценивается консервативно по снижению дневного остатка;
другие потребители могут завысить оценку. Первую неизвестную стоимость
невозможно гарантированно узнать заранее: ограничение провайдера всё равно
обрабатывается остановкой до сброса. Внешние интеграции также расходуют квоту.

## Общий бюджет без миграции

API-проверки и telephony-worker используют одну PostgreSQL. В существующей
таблице глобальных счётчиков `auth_throttles` находятся отдельные SHA256-ключи
с пространством имён Novofon Data API. Сохраняются только числа и временные
метки: без API-ключей, номеров, ссылок и содержимого звонков. Нулевой остаток
кодируется как attempts=1. Прежние login-счётчики не меняются. Существующая
очистка старых throttle-строк безопасна для активных будущих сроков сброса.

До HTTP выполняется атомарное резервирование бюджета с advisory-lock по
хэшу токена и, когда аккаунт установлен, по хэшу аккаунта. Разные ключи одного
известного аккаунта делят его бюджет. Неизвестный аккаунт можно связать только
после первого `get.account`; внешние и ещё не связанные ключи заранее учесть
невозможно. Транзакция заканчивается до сетевого запроса. Остатки и cooldown
сохраняются отдельно от успеха загрузки страницы и переживают перезапуск.
Запоздавший/параллельный ответ не возвращает уже зарезервированные единицы.

При HTTP 429 учитывается Retry-After (секунды или HTTP-date); при -32029 —
тип лимита и metadata/reset. Следующий запрос выполняется не раньше этих
сроков и собственного безопасного темпа. Внутри HTTP-клиента нет sleep и
автоматических повторных POST. Загрузчик переносит due_at/retry_at, сохраняет
курсор и уже полученные звонки, не отключает доступ к сохранённому аудио.
Неизвестный -32029 без метаданных останавливает запросы осторожно до
дневного окна; некорректный/отсутствующий Retry-After не даёт частых повторов.

Проверенные account/timezone кэшируются на час для той же версии реквизитов.
Изменение ключа всегда требует нового `get.account`. Открытие карточки,
перерисовка ленты и монитор загрузки не обращаются к Data API. В мониторе
показывается учтённый остаток и понятная пауза с датой автоматического повтора.
Выбранный интервал загрузки остаётся желаемой частотой, а не способом обойти квоту.

## Выпуск API и телефонии без перезапуска MAX

`prepare_telephony_update.py` требует точный текущий main, чистый checkout,
ожидаемые API/MAX/telephony образы, предыдущую и новую policy. Под прежним
deploy-lock он явно устанавливает проверенный guard и записывает точный
план обновления телефонии. Затем работает только прежний
`ramessenger-local-build.service`, без GitHub Actions и второго контроллера.

Compose и ревизия 0031 остаются прежними. Перед заменой — весь pinned
offline/PostgreSQL gate без skips и проверенный дамп. Обновляются telephony
и API; ID и image ID MAX сверяются до и после. Обычный API-выпуск не меняет
оба worker. Новый телефонный контракт без подготовленного плана блокируется.

План и исходные env/runtime-state хэшируются до замены. При сбое или
прерывании восстанавливаются прежние pin/metadata и API/telephony, включая
случай отсутствующего контейнера после прерванного recreate. Чужой процесс,
изменённый MAX, Compose или восстановительные файлы требуют разбирательства,
а не перезаписи. База из старого дампа не накладывается, новые звонки не удаляются.

контейнеров обязательны все 228 offline и 81 PostgreSQL проверка без skips.
