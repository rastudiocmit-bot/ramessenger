# Задержки вкладок после ввода SIP-линий

## Подтверждено в коде и воспроизведено

- Открытие «Подключений» ожидало загрузку всех секций: ИИ, CRM, MAX и
  загрузчика карточек. Возврат на Новофон зависел от завершения скрытого ИИ.
- После ожидания старая функция навигации заново проверяла текущую вкладку
  и повторно запускала уже выбранный раздел, например «Задачи».
- Поздний статус ошибки MAX мог переключить выбранный Новофон обратно на
  мастер. Скрытый отчёт MAX продолжал опрашиваться в разделе Новофона.
- Повторные переходы читали SIP-реестр заново и временно блокировали его форму.
- Обычные GET без явного timeout могли ждать ответа без ограничения.

Сохранение SIP-линии выполняет локальные проверку, шифрование и запись в БД.
Оно не вызывает регистрацию SIP или API Новофона. Без замеров на VPS нельзя
приписать сообщённую минутную паузу конкретной серверной операции.

## Изменение поведения

Подгружаются данные выбранной секции. Поздний запрос не запускает новую вкладку
и не переключает её. Просмотр отчёта MAX приостанавливается вне мастера;
серверная синхронизация MAX продолжает работать независимо от этого просмотра.
GET по умолчанию ограничен 12 секундами, явно заданные сроки сохраняются.
Timeout операций записи этим изменением не сокращается.

SIP-список автоматически переиспользуется до 30 секунд в рамках той же
организации, пользователя и эпохи сессии. «Обновить список» всегда читает БД.
Изменения пароля, сотрудника, ведущие нули, версии, защита от дублей и проверка
прав на сервере сохраняются. Кэш не подтверждает регистрацию или работу линии.
При ожидании ответа на SIP-запись остальная навигация доступна; автоматический
повтор записи или проверка API Новофона не выполняются.

## Проверка

372 UI-теста, включая сценарии медленных ответов, смены вкладки, таймаута GET,
кэша по сессии/организации и его принудительного обновления. Проверка Chromium
на ширинах 1440/390 удерживает ответы ИИ, MAX и сохранения SIP, проверяет
доступность других вкладок, единственную запись и ручное обновление.
Это синтетические ответы; время живого сервера отдельно не измерялось.

Обычный выпуск через `ramessenger-local-build.service`, без смены policy,
схемы, серверного SIP-кода, MAX/telephony images или настроек провайдера.

Если задержка сохраняется, во время неё собрать только нагрузку и состояние
ожидания БД, без текстов запросов, SIP-паролей и ключей:

```bash
docker stats --no-stream --format '{{.Name}} CPU={{.CPUPerc}} MEM={{.MemUsage}}' center-messenger-api-1 center-messenger-db-1 center-messenger-max-worker-1 center-messenger-telephony-worker-1
docker exec center-messenger-db-1 psql -X -U cm_owner -d center_messenger -c "SELECT pid,state,wait_event_type,wait_event,round(extract(epoch FROM clock_timestamp()-query_start)::numeric,1) AS seconds,pg_blocking_pids(pid) AS blockers FROM pg_stat_activity WHERE datname=current_database() AND pid<>pg_backend_pid() AND state<>'idle' ORDER BY query_start LIMIT 12;"
```
