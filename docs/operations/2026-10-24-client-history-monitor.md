# Подробный монитор обработки клиентов

Страница «Подключения» разделена на вкладки «Монитор загрузки» и
«Настройки сервисов». Монитор содержит состояние трёх этапов, текущую
операцию, клиента и карточки AlfaCRM, порядковый номер обработки, ID
исходной записи, филиал и страницу журнала, направление и время.
Формы доступа к CRM и MAX, филиалы и MAX-боты находятся в настройках.

## Что показывается в прямом наблюдении

Обработчик перед проверкой клиента и перед проекцией каждого получателя
публикует его настоящие имя и ID AlfaCRM. Для массовой рассылки получатели
показываются отдельно; карточки одной подтверждённой семьи перечисляются
вместе. ID передаются строками, включая значения больше точности JavaScript.
Текст сообщений, телефоны, email, токены и браузерная сессия в монитор
не добавляются. Доступ использует прежнее административное разрешение
API подключений и ограничение текущей организацией.

При чтении страницы CRM ещё нет текущего клиента. Монитор показывает
журнал и страницу и не приписывает предыдущего клиента новой странице.
Быстрые операции между обновлениями экрана остаются в списке последних
30 операций. Выбор строки открывает её сведения; «К текущей операции»
возвращает наблюдение. История пользователя при обновлении не прокручивается
автоматически к новым строкам.

Состояние «В обработке» не подтверждает запись в базе. Только после
успешного завершения транзакции результат становится «Проверено»,
«Сообщение сохранено» или «Отправка сопоставлена». Если транзакция
откатилась, её диагностические записи помечаются «Не сохранено · повторим».
Номер клиента относится к проверке справочника; номер записи на странице
относится к сообщению, поскольку журнал CRM разбит по сообщениям.

## Технические границы

Диагностика текущего клиента хранится под отдельной блокировкой памяти
в том же процессе, что фоновый обработчик. Штатный контейнер запускает
один процесс Uvicorn. Это позволяет видеть длинную незавершённую транзакцию
без частичных коммитов сообщений и без дополнительных записей в базу
на каждого клиента. Снимок выдаётся только для совпадающих организации,
подключения и действующей аренды обработчика. Защита записи и курсоры
синхронизации не зависят от монитора.

Последние подтверждённые операции сохраняются вместе с курсором. После
перезапуска или при чтении из другого процесса доступен этот снимок
с подписью «Последний отчёт», а не имитация текущего клиента. Журнал
ограничен 30 операциями и не заменяет постоянный аудит всех сообщений.
При необходимости нескольких API-процессов наблюдение за текущим клиентом
потребует общего канала диагностики; сохранённые позиции уже общие в БД.

Открытый монитор получает состояние каждую секунду. Четыре из пяти
запросов используют `sync-progress?activity_only=true`: только настройки,
очередь и диагностика, без подсчёта всей истории. Каждый пятый запрос
обновляет полные числа и журналы. В настройках интервал 5 секунд;
при сетевых сбоях действует прежняя задержка повторов 2–30 секунд.
При уходе из раздела, смене организации и выходе диагностика очищается,
опрос прекращается. Серверная загрузка продолжается независимо от окна.

Дополнительно исправлено чтение дат очереди: PostgreSQL `-infinity`
между проходами не декодируется psycopg как обычная дата. Неограниченные
служебные даты возвращаются как `null`, а признаки аренды вычисляются
по исходным SQL-значениям. Исправление покрыто проверкой статуса после
завершения прохода.

## Рабочий отчёт пользователя

В предоставленном отчёте от 24 октября, последнее чтение 19:33 по Москве,
проверка 3741 клиента завершена. У исходящего журнала филиала 2 проверена
страница 878 (индекс 877), недостаёт одной исходной записи. У филиала 4
недостаёт девяти, повтор назначен на 25 октября 00:10 по Москве.
283 старые записи не имеют подтверждённого исходного ID. Совпадение
числа сохранённых и ожидаемых записей в других журналах не доказывает
полноту этих старых записей. Этот выпуск не объявляет их исправленными
и не запускает заново уже завершённую проверку клиентов.

## Проверки и установка

104 серверных теста: 103 успешны на PGlite; один тест конкурентных
блокировок требует нативной PostgreSQL и явно пропущен. Проверены
границы аренды/организации, ограничение журнала, состояния сохранения
и отката, реальные ID в незавершённой обработке и лёгкий статус без
агрегатных запросов. 56 тестов интерфейса успешны, включая выбор записи,
большие ID, безопасное отображение имени и очистку прежней организации.
Chromium 153 проверяет состояния загрузки, повторный вход, раздельные
вкладки, светлую/тёмную темы, ширину 390 px и восстановление после 503
и таймаута. Браузерные проверки используют синтетические данные.
Также пройдена общая проверка кабинета для пяти ролей, включая ограничения
доступа к настройкам, отправку и карточку семьи, с отключённой анимацией.

Миграций и новых зависимостей нет. Полученные отдельно изменения
карточки семьи и таймера автоматической установки сохранены.
Docker и рабочая аутентифицированная CRM в среде подготовки недоступны.
Установка использует существующий процесс:

```sh
systemctl start ramessenger-local-build.service
docker inspect --format '{{.Config.Image}}' center-messenger-api-1
```

После обновления страницы через Ctrl+Shift+R открыть «Подключения» →
«Монитор загрузки». Полноту рабочей истории проверять свежим
`python -m center_messenger.history_audit`; монитор не скрывает
расхождения и не удаляет старые сообщения.
