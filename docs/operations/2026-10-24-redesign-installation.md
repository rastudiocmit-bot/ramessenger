# Подготовка полного нового кабинета к установке

Перенесена композиция из пользовательского архива `razvivaysya-redesign (2).zip`,
включая ролевые `reference/*.html`: узкое меню с иконками, список диалогов,
фон и пузыри переписки, мобильное нижнее меню, карточки разделов и профиль.
Рабочий кабинет использует свои API и сохранённые данные. Демонстрационные
клиенты, показатели и имитация отправки из прототипа в приложение не переносятся.

## Состав выпуска

`index.html` загружает `appearance.js?v=2.0` до CSS, затем `app.css` для
существующих форм и новый `cabinet.css?v=2.0`. Старый частичный `redesign.css`
удалён. `icons.js` содержит SVG из макета; логотипы и обои также взяты из архива.
Inter хранится локально вместе с OFL-лицензией; внешняя загрузка шрифтов не нужна.
`cabinet.js` управляет новым меню, профилем, мобильной навигацией и сводкой.

Сводка вычисляется на сервере по видимым сохранённым сообщениям: обращения,
ожидающие ответа диалоги, новые лиды и среднее время первого подтверждённого
ответа сотрудника. Автоматические сообщения и повторные ответы не сокращают
время ответа. Семь календарных дней рассчитываются в часовом поясе центра.
Пока идёт восстановление истории, показатели могут уточняться.

Для входа в чаты используется отдельный `/chats/context` с безопасными
метаданными каналов и филиалов. Просмотр переписки сотрудниками больше не
требует доступа к административным API настройки подключений. Карточка семьи
читается через связанный диалог, с повторной проверкой контакта и организации.

## Тема и уведомления

«Профиль» → «Вид» → «Тёмная тема». По умолчанию тема светлая; системная тема
её не переключает. Дополнительный выбор доступен в настройках мессенджера.
Выбор хранится в `localStorage` (`cm-theme`), применяется до загрузки CSS
и синхронизируется между вкладками одного сайта. Если браузер запрещает
сохранение, тема действует в открытой странице, а рядом появляется пояснение.

В профиле отдельно настраиваются звук и показ текста уведомления. Громкость
и сигналы для статусов открываются кнопкой «Сигналы». Эти настройки относятся
к браузеру пользователя. При выключенном превью уведомление скрывает имя и текст.

## Счётчик: актуальная инструкция

Рабочий список получает `unread_count` от сервера. Синий круглый бейдж
`span.ava-n.avatar-count` создаётся внутри аватара при положительном значении;
на экране показывается `Math.min(unread_count, 99)`, в доступном названии —
полное число. При нуле бейджа нет. Размер, палитра и размещение сохранены из
нового макета. Непрочитанные на клиенте заново не рассчитываются.

Инициалы используют первые два слова имени. Аватар и заголовок диалога
открывают действующую карточку семьи. Автоматические сообщения свёрнуты
в компактную строку и раскрываются без потери состояния при обновлении истории.

## Прокрутка и история

Список использует `.list.chat-list-scroll`, переписка — `#chat-stream.stream`,
остальные страницы — `.scroll`. Скрываются дорожки полос прокрутки; сами
контейнеры сохраняют `overflow-y:auto`. На телефоне переписка открывается
на весь экран, а кнопка «Назад» возвращает список и нижнюю навигацию.

Курсоры сообщений, границы страниц, порядок по времени и исходным CRM-ключам,
сохранение черновиков и защита от повторной отправки сохранены. Загрузка старой
страницы удерживает видимое сообщение на месте. Никакие сообщения из рабочей
базы этот выпуск не удаляет и не объединяет. Worker восстановления истории,
его позиции и внутренний браузер не меняются; закрытие окна пользователя
не останавливает приём и восстановление на сервере.

## Права и действующие ограничения

Меню учитывает роль и выданные разделы. Настройка интеграций, полная CRM-загрузка
и управление сотрудниками остаются административными. Руководителю филиала
и наблюдателю с доступом к сообщениям доступен список контактов только из
доступных диалогов, без запуска синхронизации. Оператор открывает семью из чата.
Наблюдателю сервер запрещает отправку, отметку «обработано» и смену привязки.

В текущей модели ещё нет назначения сотрудника на конкретные филиалы: название
роли «Руководитель филиала» само по себе не создаёт такое ограничение. Выпуск
сохраняет существующий охват сообщений организации; новое распределение
по филиалам требует отдельной модели прав.

Скрепка оставлена в композиции, но отключена: действующий канал не поддерживает
отправку вложений (`send_attachments:false`). Быстрые ответы заполняют черновик;
отправка выполняется только по команде сотрудника. Имитация загрузки файлов
из демонстрационного макета не используется.

## Проверка

На изолированной базе PGlite выполнены 89 серверных тестов: 88 успешно,
одна проверка конкурентных PostgreSQL-транзакций пропущена, поскольку для неё
нужен отдельный нативный PostgreSQL. Пройдены все 44 jsdom-теста интерфейса.
Проверки Chromium 153 выполняются только с синтетическими API-ответами:

- `test:cabinet`: пять ролей, ограничения разделов, отправка с CSRF/request_id,
  отметка «обработано», карточка семьи, список клиентов, управление ролью,
  проверка бота, профиль, сеансы и отсутствие обращений сотрудников к API настройки.
- `test:appearance`: явная тема, сохранение после перезагрузки и между вкладками,
  синий счётчик, 500 px прокрутки списка, мобильные список и переписка при ширине 390 px.
- `test:scroll`: 201 сообщение без повторов, подгрузка колесом и сохранение
  видимого сообщения; смещение при изменении истории менее одного пикселя.
- `test:progress`: зависший запрос статуса прерывается по таймауту, опрос
  восстанавливается и прекращается при уходе из раздела.

```sh
npm ci --ignore-scripts
npm test
npm run test:cabinet
npm run test:appearance
npm run test:scroll
npm run test:progress
python3 -m compileall -q app/backend/src app/backend/migrations scripts
python3 -m unittest discover -s tests -p 'test_*.py' -v
```

Для браузерных проверок нужен установленный Chromium; при необходимости задать
`CM_TEST_CHROMIUM_EXECUTABLE` и `CM_TEST_CHROMIUM_ARGS` (JSON-массив).
`CM_APPEARANCE_SCREENSHOT_DIR` включает сохранение снимков.
Для серверных тестов задать `CM_TEST_DATABASE_URL` на изолированный PostgreSQL.

Docker в локальной среде подготовки отсутствует: сборка контейнера и
`docker compose config --quiet` здесь не выполнялись. До установки рекомендуется
запустить штатный workflow `Verify Center Messenger` на ветке выпуска:
он проверяет нативный PostgreSQL, Compose, сборку и граф миграций и не деплоит сервер.

## Установка и откат

Изменения подготовлены в `prepare/redesign-settings-20261024`, PR #6.
Автоматическая установка в ходе подготовки не запускается. До слияния этой
ветки в `main` повторный запуск службы на VPS не установит новый кабинет.

После проверки и слияния используется существующий процесс:

```sh
systemctl start ramessenger-local-build.service
docker inspect --format '{{.Config.Image}}' center-messenger-api-1
journalctl -u ramessenger-local-build.service -n 100 --no-pager -o cat
```

Проверить готовность API, обе темы, список и прокрутку истории, профиль
и права тестового сотрудника. Полнота данных рабочей CRM подтверждается
отдельно штатным `python -m center_messenger.history_audit`; локальные макеты
не доказывают завершение восстановления на сервере.

Миграции, зависимости Python, Dockerfile и контроллер установки не меняются.
Для отката кода используется предыдущий API-образ через штатную процедуру;
восстановление рабочей базы из старой копии для смены оформления не требуется.
