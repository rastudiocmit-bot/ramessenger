# Несколько ИИ: доступ и деплой мессенджера

Целевой проект — только `rastudiocmit-bot/ramessenger`. Доступ других проектов,
общий прокси, Compose, тома и первоначальный серверный таймер не меняются.
GitHub Actions не используется. Работа над одним файлом может потребовать
разрешения конфликта при объединении веток; серверная очередь решает другую
задачу — сериализует выпуск уже объединённого `main`.

## Путь запроса

1. Исполнитель делает изменения в своей ветке, проверяет их и объединяет с
   актуальным `main`, сохраняя чужие коммиты. Force push запрещён.
2. Его отдельный SSH-ключ привязан к actor и роли на постоянной учётной записи
   `cm-support`. Команда `deploy <40-символьный SHA>` принимается только для
   текущего `main`, записывается в SQLite и получает UUID запроса.
3. `ramessenger-support-queue.service` обрабатывает запросы последовательно.
   Разрыв SSH после приёма не прерывает systemd и не удаляет запрос.
4. Очередь вызывает **существующий** `ramessenger-local-build.service`.
   Он владеет общей `.deploy.lock` на всём пути: сборка, бэкап, миграция,
   пересоздание API, готовность и возможный откат.
5. До бэкапа и после него runner повторно проверяет `main` и активный образ.
   Сборка старого коммита не продвигается, если к этому моменту `main` обновился.
   После последней проверки начинается неделимая относительно других деплоев
   фаза продвижения выбранного SHA. Новый коммит, пришедший позднее, ждёт её
   завершения. Историческая успешная установка остаётся успешной в журнале.
   Отдельная проверка предка запрещает автоматическое понижение версии после
   reset/force push main; такой выпуск требует ручного разбора. Это не мешает
   штатному откату неудавшейся установки под тем же lock.
6. После готовности, совпадения образа и записанного runner SHA запрос получает
   `deployed`. `queued` и `running` ещё не означают установку.

Состояния: `queued`, `running`, `deployed`, `superseded`, `failed`.
`superseded` означает, что main изменился до запуска/продвижения этой версии.
Если один запрос ожидал завершения ранее начатого systemd job, очередь сверяет
фактически установленный SHA и при необходимости запускает runner ещё раз.
После сбоя работника `running` восстанавливается и сверяется с установленной
версией. Уже установленный SHA не выкладывается повторно.

Таймер очереди раз в 20 секунд читает локальную SQLite. При пустой очереди он
не обращается к GitHub и не запускает Docker/деплой. Он закрывает гонку между
поступлением запроса и завершением предыдущего worker. Исходный таймер проверки
main продолжает работать с прежним расписанием.

## Установка

Сначала интегрируйте эту ветку в main и дождитесь установки обновлённого
`local_build_vps.py` обычным серверным механизмом. Установщик проверяет наличие
защиты `fresh_source_before_promotion` и отказывается устанавливать поддержку
из коммита, который ещё не вошёл в main.

На сервере нужны существующий каталог `/opt/center-messenger-github`, root,
Python 3, gh с доступом к этому репозиторию, OpenSSH и sudo/visudo. Не меняйте
настройки SSH/межсетевого экрана вслепую; IP и порт берутся из текущего доступа
владельца. Установка не добавляет порт и не открывает браузерный DevTools.

В PuTTY/обычном SSH-терминале скачайте установщик **по точному SHA** и выполните
из файла. Не вставляйте here-doc в однострочную консоль WinSCP. Публичный ключ
не является секретом; приватный ключ остаётся у конкретного исполнителя.

```bash
gh api 'repos/rastudiocmit-bot/ramessenger/contents/scripts/install_support_access.py?ref=FULL_INTEGRATED_SHA' -H 'Accept: application/vnd.github.raw+json' > /tmp/cm-install-support.py && python3 /tmp/cm-install-support.py --ref FULL_INTEGRATED_SHA --actor chatgpt-20261028 --role maintainer --public-key 'ssh-ed25519 PUBLIC_KEY_BASE64'
```

Постоянная учётная запись — `cm-support`; пароль заблокирован. Для нового ИИ
повторите установку с новым actor и **его собственным ключом**. Повторная
установка того же actor заменяет только его строку ключа. Права:

| Команда | diagnostic | maintainer |
| --- | --- | --- |
| `status` | да | да |
| `logs` — последние 300 строк API за 30 минут | да | да |
| `deploy-logs` — журнал двух сервисов мессенджера | да | да |
| `audit` — GET-only проверка MAX-адресатов | да | да |
| `deploy <current-main-sha>` | нет | да |

Произвольная оболочка, Docker-команды, SQL, изменение Compose, БД, прокси и
других проектов через этот доступ не предоставляются. Ключи имеют `restrict`
и фиксированную команду входа; shell-подстановки не выполняются. Запросы и
actor фиксируются в `support/requests.sqlite` и `support/events.jsonl`.
Журналы и диагностические результаты могут содержать клиентские данные —
выдавайте доступ только соответствующим исполнителям.

Проверка соединения после сверки публичного отпечатка ключа сервера с владельцем:

```bash
ssh -T -i /path/to/own/private_key -p SSH_PORT cm-support@SERVER_IP status
ssh -T -i /path/to/own/private_key -p SSH_PORT cm-support@SERVER_IP audit
ssh -T -i /path/to/own/private_key -p SSH_PORT cm-support@SERVER_IP deploy FULL_MAIN_SHA
```

Не отключайте проверку host key. При очистке рабочей среды ИИ приватный ключ
может исчезнуть: замените публичный ключ actor или отзовите старый. Учётная
запись сама по себе не означает доступ ИИ между чатами или постоянную фоновую
работу ИИ.

### Если диагностике мешает занятый браузер

`audit` запускает один процесс: до 210 секунд ожидает освобождения штатного
browser lease, затем до 120 секунд проверяет формы GET-запросами. Новые
отправки, замеченные в очереди при проверке состояния, задерживают старт
необязательной диагностики. Приоритеты рабочего планировщика не меняются. Диагностика
не снимает чужие блокировки, не останавливает загрузчик и не отправляет сообщения.
Это ограниченное ожидание, а не гарантированное место в очереди загрузчика.

При ожидании в JSON сохраняются состояние подключения, необходимость проверки
сессии, остаток TTL браузера, наличие выполняющейся синхронизации и число
ожидающих отправок. Это признаки конкуренции, а не доказательство владельца
browser lease. Токены, cookies и тексты сообщений не выводятся.
`browser_wait_timeout` означает, что за отведённое время проверка не началась;
`session_check_pending` и `connection_not_active` требуют разбора авторизации.
Эти состояния не подтверждают исправность или неисправность форм отправки.

Обёртка сообщает о работе каждые 10 секунд и ограничивает запуск 360 секундами.
Второй одновременный `audit` возвращает `audit_running`. Чтобы закрытие WinSCP
не прерывало проверку, root может запустить её в фоне и позже прочитать файл:

```bash
nohup /usr/local/sbin/cm-support-control --actor ACTOR --command audit > /opt/center-messenger-github/support/recipient-audit.log 2>&1 < /dev/null &
tail -n 120 /opt/center-messenger-github/support/recipient-audit.log
```

Изменения скриптов поддержки устанавливаются повторным запуском установщика
по точному интегрированному SHA; обычный деплой контейнера не заменяет
`/usr/local/sbin/cm-support-control`. Повторная установка сохраняет других actor.

Отзыв (root на VPS):

```bash
python3 /opt/center-messenger-github/support/install_support_access.py --actor chatgpt-20261028 --revoke
```

Проверка роли повторяется непосредственно перед обработкой очереди, поэтому
отозванный actor не может запустить ещё не начатый запрос. Уже начатое
продвижение безопасно завершает готовность/откат. Доступ остальных actor и
исходный таймер остаются работоспособными. Для полного отключения очереди:
`systemctl disable --now ramessenger-support-queue.timer`; не прерывайте
активный build/migrate процесс и не удаляйте его lock-файл.

## Границы гарантий

- Блокировки защищают участников, использующих этот механизм. Другой проект
  с unrestricted root/Docker всё ещё может удалить чужие контейнеры/ресурсы.
  Его доступ и общий прокси должны быть изолированы независимо.
- Прокси этим установщиком не меняется. Будущие изменения общего Caddy/nginx
  требуют общего host-wide lock, проверки конфигурации и атомарного применения;
  отдельные проектные deploy locks для этого недостаточны.
- Runner уже доверяет deploy-скриптам из main и обновляет их с root-правами.
  Поэтому участник с возможностью изменять main остаётся доверенным участником
  инфраструктуры; ограниченный SSH не является защитой от вредоносного кода
  в main. Проверка изменений и GitHub-защита main нужны отдельно.
- AGENTS.md — инструкция исполнителям, а не принудительная GitHub-блокировка.
  В GitHub следует запретить force push/удаление main и использовать PR;
  пользовательские правила репозитория этот установщик не меняет.
- Миграции/откат используют существующую проверенную логику, не новый
  восстановитель БД. Новые изменения схемы требуют обычной проверки совместимости.

## Проверки перед выпуском

`python3 -m unittest discover -s tests -p 'test_support_access.py' -v`
проверяет отдельные процессы/lock, параллельную запись очереди, рестарт,
отзыв роли, проигранную гонку пробуждения, устаревший main, ошибку деплоя,
ожидание предыдущего job и отсутствие shell-инъекции. Тесты не подключаются
к VPS и не вызывают Docker. Проверки отката остаются в
`test_github_deploy_rollback.py`, GET-only диагностики — в
`test_recipient_diagnostic.py`. Доступность SSH и systemd на реальном VPS
проверяется после установки, а не подменяется результатами unit-тестов.
