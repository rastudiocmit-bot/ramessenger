# Проверка загрузки и дублей сообщений — 24 октября 2026

Проверен `rastudiocmit-bot/ramessenger`, исходная версия
`a264b37f1ef040d00d8f4506b16bcd631fcb43ad`. Главный путь получения MAX —
серверный Playwright/Chromium, сохранённая сессия AlfaCRM и обход штатных журналов
`/company/{branch}/max/receive` и `/company/{branch}/max/sent`.
MAX Bot API проверен дополнительно как отдельный источник.

## Проверки

- 34 регрессионные проверки проекции, чтения, повторного опроса и браузерного
  разбора; ещё 5 существующих проверок отката развёртывания.
- 15 проверок интерфейса на реальном HTML/JavaScript приложения в jsdom.
- Воспроизведение исходной версии в отдельной рабочей копии: первоначальный
  набор из 28 серверных проверок выявил 23 сбоя, из 10 проверок интерфейса — 9.
  Это количество проверок, а не количество независимых причин.
- Python-проверки выполняются с точными зависимостями `requirements.txt`.
  Локально SQL исполняется движком PostgreSQL в PGlite через PostgreSQL wire
  protocol; применяются все 12 миграций. Проверки не заменяют нагрузочный тест
  обычного PostgreSQL с несколькими соединениями.
- Ручной GitHub workflow дополнен PostgreSQL 16 и обоими наборами тестов.
  Автоматический запуск Actions и публикация этим workflow не включены.
- Синтаксис Python/JavaScript и граф миграций проверены; текущая вершина
  `0012_member_sections` сохранена, новых миграций нет.

## Границы проверки и применение

Публичные `/health/ready` и `/api/system/info` отвечают: `ready`, версия `0.8.1`.
Это подтверждает доступность API, но не полноту загрузки истории AlfaCRM.
Реальная авторизованная сессия, журналы рабочего Chromium, текущие записи
PostgreSQL и доставка сообщений в реальные аккаунты в этой проверке недоступны.
Тесты используют вымышленные данные и не отправляют сообщений клиентам.
Docker-образ локально не собирался: Docker в среде проверки отсутствует.

При первом запуске исправленной версии история один раз перечитывается для
восстановления старых ошибочных связей. Это временно увеличит число обходов
AlfaCRM. До публикации нужен сохранённый дамп с проверенной возможностью
восстановления: возврат прежнего образа сам по себе не отменяет исправление
связей сообщений. Физическое удаление истории не выполняется; доказанные эхо
помечаются и скрываются.

После публикации нужно проверить на реальной сессии: движение курсоров по
каждому филиалу и обоим журналам, завершение первичного обхода, соответствие
последних строк AlfaCRM списку и открытому диалогу, отсутствие повторов после
нескольких опросов и сохранение очереди/черновиков при объединении. Отдельно
сопоставить потенциальные повторы из разных журналов: разные идентификаторы
нельзя автоматически склеивать только по совпадению текста.

Для дальнейшей оптимизации полезно измерить длительность обхода и число
запросов к AlfaCRM, задержку до появления последнего сообщения и длительность
SQL списка. Длинные открытые переписки сейчас полностью перерисовывают DOM;
виртуализация истории и уменьшение пустых опросов могут снизить нагрузку.

## Дополнение: в диалоге видно одно сообщение

После уточнения пользователя отдельно проверено отображение всей переписки.
Публичный `/assets/chat.js?v=0.8.14` побайтово совпал с исходной веткой `main`,
а не с исправлениями PR. SHA-256: `bb63babff29d7d20a8cff9af83001ef280b8c098ee6d97ad7cf3ed47f85627f8`.
Таким образом, рабочий сайт на момент проверки продолжал использовать прежнюю
логику; конкретное количество записей в рабочей базе без авторизации неизвестно.

Отдельно воспроизведён дефект интерфейса: при одном коротком сообщении и
`has_more=true` нет полосы прокрутки, а загрузка ранних сообщений запускается
только событием прокрутки вверх. Исправление автоматически заполняет видимую
область ранними страницами и добавляет кнопку «Загрузить более ранние сообщения».
При ошибке доступен повтор; уже отображённые сообщения сохраняются.

API возвращает число сохранённых сообщений и состояние загрузки AlfaCRM.
Под перепиской показано количество отображённых сообщений, а при незавершённом
обходе — понятный статус дозагрузки. Это различает ещё не полученную из CRM
историю и страницы, уже доступные на сервере. Ошибка синхронизации также видна
внутри диалога. Версии JS/CSS в HTML обновлены для получения новых ресурсов.

Четыре новые проверки интерфейса сначала воспроизвели сбои, затем прошли:
короткая история без прокрутки, повтор после ошибки, полный вывод 50 сообщений
одного клиента и статус ожидания AlfaCRM. Весь набор: **39 Python + 15 JS = 54**.
