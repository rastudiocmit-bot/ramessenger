# Полная резервная копия мессенджера

`scripts/full_backup_vps.py` запускается явно от root. Он не выкладывает код,
не изменяет схему, не заменяет образы и не подключает новые каналы. Утилита
поставляется отдельно от основного приложения; для запуска не нужен коммит в
main, GitHub Actions или изменение штатного таймера деплоя.

## Состав

- Все существующие `/opt/center-messenger*`, включая скрытые файлы, ключи,
  секреты, старые релизы и уже имеющиеся архивы. Ничего из них не удаляется.
- Смонтированные файлы/тома API и PostgreSQL. Работающий PGDATA не копируется
  обычным tar: полный кластер сохраняется через PostgreSQL `pg_basebackup`
  вместе с WAL и манифестом SHA-256.
- Дополнительные логические дампы всех обычных подключаемых баз и глобальных
  объектов PostgreSQL. Оглавление каждого дампа проверяется `pg_restore`.
- Точные работающие образы API и БД через `docker image save`, полный Git bundle
  репозитория с проверкой наличия коммита работающего образа.
- Конфигурация Nginx, сертификаты, зависимости прокси, systemd/drop-in и
  EnvironmentFile, скрипты поддержки, доступ support, root SSH/GitHub/Docker
  credentials и сведения о пакетах. Эти чувствительные файлы только читаются
  и попадают исключительно в зашифрованные части.
- Устойчивая копия SQLite очереди поддержки через ее online backup API.
  Живые WAL/SHM этой очереди не копируются вместо согласованного снимка.

Это комплект для восстановления мессенджера и его окружения, не образ всего
диска с данными остальных сайтов. Временная память процессов и tmpfs не являются
постоянными данными; веб-сессия AlfaCRM хранится зашифрованно в PostgreSQL.

## Порядок

1. Создать приватные каталоги копии и отдельного ключа. Проверить инструменты,
   состав контейнеров, привилегии, отсутствие нестандартных tablespace/unlogged
   данных, объем файлов, доступную память и консервативный запас места.
2. Временно остановить только ранее работавшие таймеры local-build/support.
   Получить существующие блокировки в порядке queue → deploy; текущий деплой
   не прерывается, чужие lock-файлы не удаляются. При занятости есть ожидание.
3. Сохранить репозиторий, файлы и образы, пока API продолжает работать.
4. Остановить ровно исходный API-контейнер с периодом на штатное завершение.
   Сохранить счетчики всех пользовательских таблиц, SQL-дампы, физическую копию
   PostgreSQL и изменяемые файлы. Сверить счетчики до/после. БД не останавливается.
5. Запустить тот же API-контейнер и дождаться `/health/ready`, сверяя ID и образ.
6. Расшифровать физическую копию в отдельный приватный каталог, выполнить
   `pg_verifybackup`, запустить из нее PostgreSQL в контейнере без сети и портов.
   Ограничения памяти/CPU применяются только к этой копии. Сверить все таблицы
   и миграционную ревизию. Проверочный контейнер не использует рабочий том.
7. Удалить только свои проверочные ресурсы, вернуть ранее работавшие таймеры,
   сохранить метаданные, повторно проверить SHA-256 и HMAC всех частей.
   Только после этого записать `BACKUP_COMPLETE` и `status.json phase=complete`.

При нехватке ресурсов или неизвестном устройстве хранения копия не объявляется
полной и рабочие данные не удаляются. Проверка выполняется на самом сервере;
локальные unit-тесты утилиты не подтверждают работоспособность серверного Docker
или доступность конкретной базы.

## Запуск

Скачать проверенный файл по точному SHA в приватный временный файл, сверить
SHA-256 кода и установить root-owned копию в `support` с уникальным именем.
Затем вызвать `/usr/bin/python3 /absolute/script.py --start`.

`--start` создает отдельный transient systemd unit с общим журналом
`/var/log/ramessenger-full-backup.log`, временем выполнения до трех часов и
независимым `ExecStopPost` для возврата исходного API и таймеров после ошибки
или аварийного завершения процесса. Обычно ресурсы возвращает сам скрипт.
Аппаратный отказ/потеря питания могут потребовать ручного запуска API.

Авторизация GitHub берется из уже работающего окружения запускающего root:
`gh auth token` вызывается внутренне с перехватом stdout. Токен кратковременно
сохраняется в приватном каталоге `/run`, передается через `LoadCredential`,
после подтвержденного старта исходный временный файл удаляется. Значение
токена не передается в аргументах, unit Environment= или журнале и не требует
повторного входа. Фоновый процесс читает защищенный credential только для
дочернего gh/git. По завершении systemd удаляет свою временную копию.

Чтение прогресса из однострочной консоли WinSCP:

```bash
tail -n 60 /var/log/ramessenger-full-backup.log
```

Копии: `/var/backups/ramessenger/<UTC-время-UUID>/`.
Отдельные ключи: `/root/ramessenger-backup-keys/<тот-же-ID>.key`.
Каталоги имеют 0700, ключи и части — 0600. Ключ не выводится и не включается
в архив. Файлы шифруются AES-256-CBC с PBKDF2 200000 и случайной солью;
целостность манифеста и частей аутентифицируется отдельным производным HMAC.

Скачать каталог копии и сохранить ключ отдельно вне сервера. Сами файлы копии
и ключи не присылать в чат. Для проверки перемещенного комплекта:

```bash
python3 full_backup_vps.py --verify /path/to/backup --key-file /separate/path/key
```

## Ограничения проверки

Физическая копия проверяется манифестом и фактическим запуском с подсчетом
таблиц. Логические дампы проверяются по оглавлению, но не восстанавливаются
повторно каждый в свою базу. Файловые архивы проверяются чтением tar/gzip,
образы сохраняются и проверяются как архив; импорт всего окружения на другом
VPS остается отдельным испытанием восстановления. Точные результаты записаны
в манифесте. `RESTORE.txt` внутри комплекта объясняет расшифровку и восстановление.
Не распаковывать системную конфигурацию поверх работающего сервера вслепую.

## Локальные проверки

```bash
python3 -m unittest discover -s tests -p 'test_full_backup.py' -v
```

Тесты используют временные файлы и вымышленные данные: шифрование/дешифрование,
подмена частей и манифеста, tar с нестандартными именами и symlink, согласованная
SQLite-копия, отказ по диску, восстановление после ошибок стадий, защита чужого
контейнера и отсутствие сети/рабочего тома у проверочной БД.
