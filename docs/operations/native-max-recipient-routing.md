# Адресат ответа через браузер AlfaCRM

Канал `alfa_max_browser` отправляет сообщения через штатную форму AlfaCRM.
Прямые API MAX-бота и AlfaCRM для этой отправки не используются.

## Выбор

1. Источник ответа — последнее видимое входящее сообщение контакта в этом
   диалоге и подключении. Удалённые, замещённые и зеркальные записи не могут
   выбирать карточку или подсказывать MAX ID. История при этом не удаляется.
2. Явный MAX ID входящего сообщения имеет преимущество. При его отсутствии
   можно использовать единственный ранее доказанный ID этого же CRM клиента
   либо подтверждённой семьи, также только из видимых входящих сообщений.
   Противоречащие явные ID блокируют отправку.
3. Если явного ID нет, каталог загружается из локального опубликованного
   снимка по точному `Customer ID`. Основной контакт определяется существующей
   моделью CRM: первым коммуникационным номером этой карточки. Выбор карточки
   для отображения справа не подменяет адресата отправки; соседние карточки по
   совпадению телефона не перебираются.
4. Одна прямая штатная MAX-ссылка карточки обрабатывается как раньше. При
   нескольких разных MAX ID допускается ссылка из строки основного номера
   этого контакта. Номер и прямая ссылка должны находиться вместе в наблюдаемой
   структуре AlfaCRM `div.col-xs-7.m-b-xs.text-right.word-break`.
5. Строка должна содержать ровно один нормализованный номер, совпадающий с
   основным номером контакта из каталога. Ссылка должна указывать на тот же
   origin, филиал, `Customer ID` и содержать явный корректный `maxUserId`.
   Из номера никогда не вычисляется MAX ID. Текст истории сообщений, широкие
   контейнеры, вторичные номера и порядок ссылок не являются основанием выбора.
6. Два разных MAX ID у одного номера, отсутствие нужной строки либо смена
   схемы CRM сохраняют блокировку `multiple_recipients`. Изменившаяся или
   устаревшая основная контактная информация требует проверки данных CRM;
   отправка другому контакту по догадке недопустима.

Проверка контакта относится к текущему диалогу основного представителя CRM.
Она не доказывает, что произвольное старое сообщение написал именно этот
MAX-аккаунт, и не объединяет вторичные аккаунты в одну личность.

## Перед отправкой и после неё

Перед POST повторно проверяются права оператора, актуальность браузерной
сессии, CRM-карточка, известный MAX ID и основной номер контакта. Изменение
этих данных отменяет подготовленную отправку до POST.

После подтверждённого принятия браузер сообщает фактические `branch_id`,
`customer_id` и `max_user_id` формы. Последний сохраняется в исходящем сообщении
только при совпадении карточки/филиала и отсутствии противоречащего ранее
заданного ID. Это помогает сопоставлять сообщение с журналом AlfaCRM.
Неизвестный результат POST автоматически не повторяется. Старые неудачные
команды сами не переотправляются.

## Проверка после установки

Перед установкой кандидат можно проверить на VPS командой
`python3 scripts/preview_native_recipient.py --ref FULL_CANDIDATE_SHA`.
Она скачивает три строго заданных Python-файла этого коммита и импортирует
кандидата только внутри одного диагностического процесса контейнера.
Рабочий API и его файлы не заменяются, используется тот же GET-only probe.
Результат выбирает последние два диалога с соответствующей ошибкой; это
не подтверждает исправность остальных диалогов и не проверяет доставку.

Сборку устанавливает существующий `ramessenger-local-build.service`; GitHub
Actions не используется. Миграции схемы для этого изменения нет.

Проверка `scripts/diagnose_max_recipients.py` не отправляет сообщений. Поля
`branch`, `customer` показывают адрес, выбранный текущим серверным кодом;
`contact_phone_tag` позволяет сравнить контакт без публикации номера;
`source.sender_resolution.selected_peer_tag` показывает выбранную прямую
MAX-ссылку. Успешное чтение формы само по себе не доказывает доставку.

После проверки требуется обычная отправка оператором и подтверждение записи
в журнале AlfaCRM и сохранности сообщения после перезагрузки чата.

Локальные проверки: `test_compose_recipient.py`, `test_native_session.py`,
`test_native_send_runtime.py`, `test_recipient_diagnostic.py`. Сценарии с
изолированным PostgreSQL и поддерживаемым PID namespace могут пропускаться
там, где соответствующая среда отсутствует; это необходимо указывать при выпуске.
