# Загрузчик истории и состояние подключений

## Воспроизведённые причины сбоев

1. Повторная ручная синхронизация сбрасывала действующую аренду фонового
   обработчика. Тот обнаруживал изменение настроек при сохранении и отбрасывал
   прочитанный проход. Теперь повторный запрос возвращает `already_running`,
   сохраняя аренду и позицию активного прохода. Постановка задачи в очередь
   также сохраняет действующую аренду того же подключения.
2. Каждая публикация справочника CRM получала новый UUID запуска и сбрасывала
   проверку сохранённых клиентов. При автоматическом обновлении справочника
   длительное восстановление могло снова начинаться с первого клиента.
   Теперь контрольная сумма соответствий филиал / ID AlfaCRM / контакт /
   доступность филиала позволяет продолжать обработку неизменившегося
   справочника. Изменение соответствий запускает проверку заново.
3. Интерфейс считал обычный приём новых сообщений загрузкой архива и показывал
   движение полосы без известного объёма. Старые строки без исходного ID
   ошибочно обозначались как пауза. Теперь завершённый архив, реальные паузы,
   ошибки подключения и записи, требующие сверки, имеют разные состояния.

Тесты воспроизвели первые две ошибки на прежней реализации. Рабочая база
и текущая аутентифицированная сессия AlfaCRM из среды подготовки недоступны:
это подтверждённые дефекты кода, но не доказательство причины каждого
расхождения в рабочем архиве.

## Новая индикация

- Отдельные карточки AlfaCRM, MAX и истории; действующие реквизиты CRM
  свёрнуты в «Настройки подключения».
- Этапы веб-сессии, обхода журналов и проверки клиентов по ID AlfaCRM.
  Полоса показывает проверенных клиентов при известном числе клиентов либо
  число пройденных журналов. Неизвестный объём не подменяется процентом.
- Три отдельных числа: видимые сообщения в переписках, все сохранённые записи
  и диалоги. Повторная сверка страниц может не увеличивать эти числа.
- Текущие филиал, направление, страница, число страниц текущего прохода
  и время последнего движения. Обработчик сохраняет эти сведения между
  браузерными запросами, до общей записи прочитанного прохода.
- Раскрываемые журналы с сохранёнными и ожидаемыми записями, последней
  проверенной страницей, неподтверждёнными ID, ошибкой и сроком повтора.
  Пауза одного журнала не скрывает работу остальных.
- Истёкшая веб-сессия раскрывает повторный вход. Отсутствие ключа CRM больше
  не представляется активной загрузкой. Ошибки просмотра статуса повторяются
  с ограниченной задержкой; отменённый по таймауту запрос не останавливает опрос.

«Обновить статус» только читает состояние. «Проверить историю» ставит проверку
в очередь либо сообщает, что текущий проход уже выполняется. В свободный
момент ручная проверка возобновляет приостановленные архивы. При активном
проходе его курсор не изменяется; сроки пауз остаются видны в журналах.

Чтение CRM выполняется внутренним браузером на сервере. Открытое окно кабинета
только опрашивает состояние. Его закрытие прекращает отображение статуса,
а серверный обработчик продолжает работу. Позиции истории и проверки клиентов
сохраняются в базе. Серверный процесс может останавливаться при перезапуске API;
после запуска очередь возобновляет работу по сохранённым позициям и срокам аренды.

Схема базы, зависимости и порядок развёртывания не меняются. Сообщения
физически не удаляются. Проверка сохранения прочитанных ID до продвижения
архивного курсора и защита от изменения настроек сохранены; при сравнении
курсоров исключены только диагностические сведения `activity`.

## Проверки

97 серверных тестов: 96 успешны на PGlite с применением всех 12 миграций;
один тест конкурентных блокировок требует отдельной нативной PostgreSQL
и явно пропущен. 51 тест интерфейса успешен.

Chromium 153 с синтетическими ответами проверяет частичную паузу, движение
страниц при неизменном числе сообщений, повторный запрос без прерывания
прохода, завершённый архив при текущем опросе новых сообщений, истечение
и восстановление сессии, светлую и тёмную темы, ширину 390 px и отсутствие
горизонтального переполнения. Дополнительно проверены пять ролей кабинета,
ограничения доступа и восстановление после 503 / таймаута статуса.

```sh
npm test
npm run test:history-states
npm run test:progress
npm run test:cabinet
python3 -m unittest discover -s tests -p 'test_*.py' -v
```

Для Python нужен изолированный `CM_TEST_DATABASE_URL`; для браузерных
проверок — установленный Chromium. Docker в среде подготовки отсутствует:
сборка контейнера и фактическая установка на VPS здесь не проверены.

## После установки

```sh
systemctl start ramessenger-local-build.service
docker inspect --format '{{.Config.Image}}' center-messenger-api-1
docker exec center-messenger-api-1 /opt/venv/bin/python -m center_messenger.history_audit
```

Сверить образ с SHA установленного `main`, обновить страницу и открыть
«Подключения». Не требуется отключать веб-сессию или очищать историю.
Реальные пропуски и неподтверждённые старые ID проверять по новому рабочему
отчёту. Код выхода аудита 2 означает незавершённую проверку или расхождения;
он не означает ошибку сборки. Полный порядок сверки источника описан
в `2026-10-24-history-progress-recovery.md`.
