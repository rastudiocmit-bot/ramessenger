# Выбор действующей карточки вместо прежнего лида

Автоматический выбор карточки для отображения не должен оставлять лид или
архивную запись только из-за старого имени представителя. CRM Customer ID,
история и получатель MAX — отдельные сущности; этот механизм не объединяет
карточки и не переписывает адресата сообщений.

## Приоритет

1. Действующий клиент с подтверждённым предстоящим занятием.
2. Действующий клиент с действующим участием в группе.
3. Действующий клиент.
4. Лид.
5. Архивная карточка.

Приоритет сравнивается до предпочтения ранее выбранной карточки. Старая
карточка сохраняется при равенстве подходящих вариантов, а не перекрывает
действующего ученика с более высоким приоритетом. Занятия другого ученика,
отменённые занятия и истёкшие группы не повышают приоритет.

## Прямое совпадение телефона

Для бывшего лида/архивного контакта рассматриваются все его нормализованные
телефоны. Подходит точное пересечение с любым телефоном текущего клиента,
включая второй телефон. Разница старого и нового ФИО при таком выборе
не запрещает показать действующую карточку.

Если несколько действующих карточек принадлежат одному представителю,
сохраняются отдельные ученики и показывается их действующая семья. Если
представители различаются, однозначно более высокий учебный приоритет может
выбрать нужную карточку. Равнозначные разные действующие семьи не объединяются
по произвольному ID/порядку; остаётся объяснимая неоднозначность.

Совпадение применяется напрямую с исходными номерами. Если исходный контакт
имеет номер A, кандидат содержит A/B, а третья карточка только B, третья
карточка не становится кандидатом. Телефоны кандидатов не расширяют поиск.
Общий номер организации также не подтверждает одну личную семью.

Имена неактивных посторонних карточек не создают ложную текущую причину
проверки у выбранного действующего клиента. Противоречия между действующими
представителями и противоречивые сведения одного Customer ID сохраняют
свои проверки. Явная ручная привязка разговора остаётся ручным выбором.

## Обновление после сканирования

Изменившаяся/новая карточка из `apply_customer` сразу пересчитывает связанные
разговоры по старым и новым телефонам в той же транзакции (до 100 контактов;
оставшиеся обрабатываются обычным фоновым проходом). Новое членство
в группе и новые факты занятий запускают тот же пересчёт. Список чатов,
статусный фильтр, поиск, правая карточка и её обновляемый кэш используют
одну сохранённую проекцию `crm.card.preference`.

Если открытая правая панель получает нового приоритетного ученика, она
переключается на него. Пока приоритетный ученик не изменился, обычные обновления
кэша сохраняют ручной выбор ученика оператором.

Политика проекции повышена до версии 2; фоновая локальная обработка заново
рассчитывает существующие разговоры порциями, без повторного импорта сообщений.
Открытие карточки также использует существующий локальный пересчёт. Прямая
телефонная группа входит в проверочную подпись: новый совпавший клиент,
изменившийся номер или статус делают устаревший выбор недействительным.

Миграция `0025_customer_phone_search` добавляет только GIN-индекс phones для
индексируемого точного поиска по всем номерам. Исходные карточки и сообщения
не меняются. Миграция обратима; readiness и release metadata согласованы
с новой версией схемы. Установка — существующий серверный build service/timer,
без GitHub Actions.

## Проверки

PostgreSQL-регрессии включают реальное старое имя лида против текущего ФИО,
приоритет действующей группы, прямой второй телефон, запрет цепочки A→B,
немедленное переключение при появлении нового действующего Customer ID,
сохранность исходных сообщений и адресата, ручные связи, фильтры/кэш,
обратимость индекса и EXPLAIN с использованием GIN. Проверки интерфейса
подтверждают переключение на нового приоритетного ученика и сохранение ручного
выбора при последующих обновлениях без смены приоритета.
