# Восстановление статуса и проверка истории AlfaCRM MAX

В рабочем отчёте от 24 октября 2026 года после ответа 503 прекратились запросы
`sync-progress`. Интерфейс оставлял анимацию и старый счётчик, а фоновый импорт
продолжался. Во втором филиале исходящий архив ещё обходился; в четвёртом
сохранялось расхождение 672/684 после достижения конца журнала. Причина самого
SQL-сбоя в исходном access log не была записана. Причина расхождения по исходным
ID пока неизвестна.

## Поведение исправленной версии

- После сетевых ошибок и 503 статус повторяется с задержкой 2–30 секунд.
  Прежние счётчики помечаются как последние полученные данные. Зависший запрос
  отменяется через 15 секунд. Параллельные запросы не создаются.
- Для каждого филиала и журнала видны сохранённые исходные записи, последняя
  проверенная страница, её время, догрузка новых сообщений и повторная проверка.
  Число сообщений отличается от числа исходных записей для массовых рассылок.
- При выходе из подключений, смене организации, отключении интеграции и выходе
  из аккаунта опрос прекращается. После полной загрузки открытый экран продолжает
  проверять состояние раз в 15 секунд.
- До продвижения позиции обхода прочитанные ID проверяются по сохранённым
  источникам и сообщениям. Несохранённая страница не считается пройденной.
  После трёх ошибок чтения или сохранения одной страницы архив приостанавливается
  на 6 часов. Если страница прочитана, остаются конкретные несохранённые ID.
- При недостаче после конца архива выполняется один дополнительный полный обход.
  Сохраняющееся расхождение приостанавливает этот архив на 6 часов и остаётся
  явной ошибкой. История не объявляется полной. Новые сообщения, их догрузка и
  независимые исправные журналы продолжают обрабатываться. Кнопка
  «Синхронизировать историю» возобновляет приостановленные архивы сразу.
- Статус, список диалогов, история и обновления читаются в `REPEATABLE READ,
  READ ONLY` без ожидания блокировок проектора. Позиция изменений и сообщения
  читаются из одного снимка. Запись и выдача последовательностей остаются
  сериализованными блокировкой организации.
- SQL-диагностика содержит операцию, класс исключения, драйвер и SQLSTATE.
  SQL, параметры, текст исключения драйвера и сообщения клиентов не выводятся.

Физического удаления сообщений, изменения соответствия клиентам AlfaCRM,
миграций схемы или изменения серверных зависимостей нет. Схема остаётся
`0012_member_sections`.

## Проверка рабочей базы

После установки обновить страницу кабинета. Текущий обход продолжается из
сохранённой позиции, повторное нажатие синхронизации ему не требуется.
Полнота истории подтверждается отчётом, а не анимацией.

Обычный отчёт без чтения CRM:

```sh
docker exec center-messenger-api-1 /opt/venv/bin/python -m center_messenger.history_audit
```

Сверка исходящего журнала филиала 4 по реальным ID без изменения сообщений,
курсоров и сохранённой браузерной сессии:

```sh
docker exec center-messenger-api-1 /opt/venv/bin/python -m center_messenger.history_audit --workspace 4f7a27e9-9b19-486d-9700-2df7784a24cb --verify-source --branch 4 --direction sent
```

Команда использует существующую зашифрованную веб-сессию и только читает страницы
AlfaCRM. База читается до обхода, соединение освобождается перед браузерным
вводом-выводом. Если импорт продолжался, отсутствующие ID следует перепроверить
новым отчётом: импорт мог сохранить их уже во время сверки. Большой журнал
проверяется долго и создаёт дополнительные запросы в CRM.

Поля `missing_ids`, `duplicate_source_ids`, `saved_not_observed_ids` ограничены
100 ID; отдельные счётчики содержат полные количества. `totals_changed` указывает
на изменение числа записей во время обхода. Дубли ID в источнике и отсутствие
сообщения в базе — отдельные результаты. Совпадение общего числа не заменяет
сверку ID. Удалённые из CRM старые сообщения в базе сохраняются.

Код 0 означает полноту отчёта без ошибок и расхождений сверки; 2 — незавершённость
или расхождения; 1 — проверка недоступна. Вывод содержит технические ID и числа,
без текстов сообщений и данных веб-сессии.

## Проверки и границы

68 проверок Python прошли на PostgreSQL-движке PGlite с применением всех
12 миграций. Ещё одна проверка конкурентных блокировок требует обычной PostgreSQL
и явно пропущена: PGlite обслуживает одно физическое соединение. Проверены
сохранение ID, остановка продвижения несохранённой страницы, ограничение повторов,
новые сообщения во время паузы, автоматическое и ручное возобновление,
независимость филиалов, сверка ID, безопасная диагностика и режим снимка.

30 тестов интерфейса прошли в jsdom. Проверка всего приложения в Chromium 153
включила 503, запрос без ответа, отмену по таймауту, восстановление счётчика и
выход из раздела, без ошибок JavaScript. Прокрутка 201 сообщения проверена
нативным колесом: смещение привязки при догрузке 0 пикселей, при смешанном
обновлении −0,5 пикселя.

Исходный 503 не воспроизводился как конкретная ошибка SQL. Изменение чтения
устраняет ожидание блокировок, но не доказывает первопричину того сбоя.
Рабочая база и аутентифицированная CRM из этой среды недоступны; окончательная
полнота рабочей истории требует рабочего отчёта.
