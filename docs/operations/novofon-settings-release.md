# Выпуск формы подключения Новофона

Форма добавляет самостоятельную `novofon_settings` и назначение `novofon`
в существующий AEAD vault. Ни одна таблица MAX/CRM и ни один алгоритм
браузерной сессии, адресации, получения или отправки MAX не меняются.
Но API и закреплённый worker проверяют точное совпадение `SCHEMA_REVISION`.
Поэтому миграцию `0029_invitation_sections → 0030_novofon_settings` нельзя
выпустить как обычное изменение API с прежним worker.

## Явно рассмотренные изменения защищённого контура

- `database.py`: новая ожидаемая ревизия и tenant-таблица настроек.
- `connector_vault.py`: только новое назначение `novofon`; AAD/шифрование MAX
  не изменяются. Секреты Новофона не размещаются в настройках AlfaCRM.
- Миграция 0030: отдельная таблица, FORCE RLS центра и администратора.
- Три штатных deploy helper: узкий парный план смены ревизии с восстановлением
  схемы до проверки старых образов при неудаче. Сам guard не отключается.
- Обязательные тесты: прежние MAX, защита настроек и миграция/RLS.

Policy явно закрепляет только переход 0029 → 0030, точный файл миграции,
его хэш и сохранение данных при downgrade. Другие миграции автоматически
не разрешаются. Публикация policy в Git не обновляет внешний guard.

## Подготовка и выполнение на сервере

1. Проверить завершённый полный бэкап, состояние API/MAX, текущие образы,
   полный API SHA, policy и ревизию БД. Дождаться окончания бэкапа и чужого
   деплоя: общий `.deploy.lock` не удалять и не обходить.
2. Получить ровно проверенный commit отдельным checkout. Установить его
   guard через `max_release_guard.py install` с точными `--expected-policy`,
   `--previous-policy` и `--expected-live`. Установщик не меняет API/БД.
3. В этом checkout выполнить:

   ```bash
   python3 scripts/max_runtime_deploy.py --update-worker --schema-from 0029_invitation_sections --source "$PWD" --sha <REVIEWED_FULL_SHA> --expected-api <LIVE_API_IMAGE> --expected-max <LIVE_MAX_IMAGE> --expected-policy <REVIEWED_POLICY_HASH>
   ```

   Команда только сохраняет точный план. Проверяются исходная ревизия,
   policy/миграция, Compose, `.env`, pin и идентичность работающего worker.
4. После публикации того же SHA в `main` запустить существующий
   `systemctl start --no-block ramessenger-local-build.service`.
   Только прежний deploy owner выполняет тесты, проверенный pg_dump,
   миграцию и переключение обоих образов под единым lock.

До DDL сохраняется `phase=migrating` с исходной/целевой ревизией, образом
миграции и его ID. После миграции worker и API переключаются обычным
проверяемым путём парного обновления. Возможен короткий период, когда
readiness старого процесса не совпадает с новой ревизией: это контролируемое
окно смены общей схемы, а не обычный API-релиз.

## Ошибка и прерывание

Если процесс завершится между COMMIT миграции и заменой worker, следующий
запуск прежде всего восстановит исходную ревизию и проверит прежние процессы.
Если замена уже началась, восстанавливаются `.env`, pin и оба старых образа;
исходная ревизия восстанавливается **до** проверки их readiness.
Посторонние изменения схемы, конфигурации или image ID блокируют автоматику
для разбора. Восстановление БД из дампа автоматически не выполняется.

Downgrade 0030 сохраняет отдельную таблицу и уже введённые за время выпуска
зашифрованные ключи; повторный upgrade идемпотентен. Сообщения, журнал,
сессии, курсоры и неоконченные отправки MAX не удаляются. Проверка rollback
не должна превращаться в восстановление старого снимка всех сообщений.

## Подтверждение результата

Нужны `MAX WORKER UPDATE COMPLETE`, `LOCAL DEPLOYED`, оба контейнера healthy,
API ready и свежая успешная синхронизация MAX. Затем открыть
**Подключения → Новофон**: поле ключа пустое, период 24 часа, сохранение
доступно администратору. После ввода ключа проверить аккаунт и журнал;
доступ к записи проверяется отдельно. Не звонить клиентам для приёмки формы.

Встроенный телефон/двусторонний звук, импорт звонков в ленту, аудиоплеер
и ИИ-расшифровка остаются отдельными этапами согласованного ТЗ.
Последующие обычные API-релизы снова не пересоздают MAX.
