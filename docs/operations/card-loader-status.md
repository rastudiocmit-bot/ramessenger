# Состояние требований к кэшу карточек, 29.10.2026

Реализовано в миграции `0028_card_loader_snapshots` и соответствующей сборке.
Это описание поведения, а не утверждение о заполненности конкретной рабочей БД.

| Требование | Реализация |
|---|---|
| Отдельные настройки | Только Мастер подключения; предзаполненные редактируемые поля и сохранённая политика организации |
| Последний полный снимок | `crm_family_snapshots`, один UPSERT всей семьи после завершения разделов |
| Сборка новой версии | Раздельные рабочие данные и страницы; старый полный снимок сохраняется |
| Смена Customer ID/ученика | Новый состав источников имеет другой ключ, чужой снимок не используется |
| Действующие без обращений | Автоподготовка, по умолчанию 12 часов, настройка 6–24 часа |
| Ожидающие ответа | Финансы и занятия по 30 минут, группы также готовятся для лидов с обращениями |
| Только действующие в фоне | Отдельный переключатель; ручное открытие остаётся доступным |
| Параллельные карточки | 1 или 2, общий лимит под блокировкой workspace, уникальные токены аренды |
| Квота API карточек | 120/мин по умолчанию, скользящее окно в БД, 6–170 в настройках |
| Уступать отправке | Настройка включена; фон останавливается между запросами, страницы сохраняются |
| Очередность | Один SQL-контракт для захвата и позиции; приоритет ручных, затем неотвеченных |
| Истечение ручного интереса | Приоритет снимается, незавершённый запрос не теряется |
| Максимальное ожидание | Настраиваемый порог усиления и явный признак задержки, по умолчанию 60 с |
| Контрольные точки/восстановление | Обязательны, сохраняются после успешных вызовов и при ожидании квоты |
| Защита доступа | RLS и права cm_app проверяются на новых таблицах |

## Границы обещаний

- Полного снимка при первом импорте ещё может не быть. До его готовности
  интерфейс показывает полученные части, а не выдумывает недостающий кэш.
- Полнота снимка означает наличие всех обязательных разделов; их время
  обновления различается согласно политике. В интерфейсе видна дата снимка.
- Указанный лимит API относится к загрузчику карточек. Остальные загрузчики
  сохраняют общий ограничитель адреса CRM и собственные бюджеты.
- Позиция очереди актуальна на момент чтения; новые срочные задачи могут её
  изменить. Задержки CRM и Retry-After не обходятся ради обещания 60 секунд.
- Безопасность, проверка ID и контрольные точки не отключаются настройками.
- Первичная фоновая подготовка всех действующих клиентов требует времени:
  добавление механизма не означает, что рабочая база уже полностью заполнена.

## Проверка

Автоматические тесты проверяют атомарную замену, сохранение старой карточки,
смену ID, подготовку действующих клиентов, квоту, паузу на отправку, два слота,
истечение приоритета, очередь и RLS. См. `tests/test_card_loader_durability.py`,
`tests/test_card_loader_settings.py`, `tests/test_card_loader_ui.cjs` и тесты
карточек/групп/занятий в `tests/test_message_sync.py`.
`tests/check_card_loader_wizard.cjs` проверяет в Chromium сохранение после
перезагрузки, восстановление после 503, черновик при смене вкладки и состояния
MAX, клавиатурную навигацию и мобильную вёрстку. Проверка использует вымышленный
API, не читает рабочие данные и не меняет настройки реальной организации.

`/health/ready` подтверждает готовность API, но отдельно не подтверждает
полноту кэша всех клиентов или длительность загрузки конкретной семьи.

## Повторная проверка 29.10.2026

- GET/PUT настроек передают Identity в транзакцию Accounts. Иначе runtime RLS
  не видит членство оператора и возвращает «Организация недоступна», хотя
  тест с вымышленным API проходит. Проверка выполняется под `cm_app`, включая
  сохранение, запрет оператору менять политику, чужую организацию и отзыв сессии.
- Выбор задания проверяет точный Customer ID/ученика/филиал через типизированный
  индексный поиск. Коррелированный поиск источника защищён от превращения в
  вложенный обход всех клиентов при устаревшей статистике. Очерёдность и позиция
  используют тот же контракт и одно время начала SQL-запроса.
- Регрессия с 2000 клиентами без ANALYZE проверяет чтение карточки и ручной
  приоритет с рабочим лимитом SQL 2500 мс. Это тестовая база, не замер VPS.
- После временного сбоя первое открытие карточки повторяется автоматически;
  стрелка работает и без первого результата. Сохранённые факты остаются на
  экране. Ответы 401/403/404 очищают приватную карточку и не повторяются как 503.
- Монитор разделяет количество клиентов и заданий. Истёкший ручной интерес
  считается фоном; задержка срочного запроса и отсутствие прогресса активной
  аренды показываются отдельно. Большой возраст задания не означает потерю данных.
- Ротация реквизитов того же подключения сохраняет полный снимок. Readiness
  также проверяет RLS/владельца таблиц снимков и состояния загрузчика.

Проверены весь Python-набор с локальным PostgreSQL-движком PGlite (762 теста,
14 пропусков, включая проверки, требующие нативной конкурентной PostgreSQL),
213 тестов интерфейса и восстановление карточки в Chromium на компьютере и
телефоне. Клиентские сообщения в ходе проверки не отправляются.
