# Изменения карточек AlfaCRM и история общения

Правило общее для любого Customer ID. Рабочий код не содержит исключений по
ФИО, телефону или номеру карточки. Отдельно учитывать ученика, представителя,
CRM-карточку, собеседника канала и исходные сообщения. Статус клиента и выбор
карточки справа не определяют автоматически адресата отправки.

## Основные сведения

`active_review.apply_customer` обновляет по точному ID только лёгкие сведения
опубликованного каталога. Отсутствующие поля сохраняются; явно переданные
пустые значения обрабатываются контрактом `customer_row`. Неполная новая
карточка без обязательных имени/статуса не создаётся. Если тот же глобальный ID
подтверждён в другом филиале единственной парой контакт/ученик, его известные
основные сведения могут заполнить пропущенные поля новой принадлежности.

Филиальные статусы сохраняются отдельно. Новый действующий клиент находится
по актуальной выдаче AlfaCRM, даже если локально он ещё лид. Шестичасовой
`ActiveReviewWorker` не обходит весь архив: отдельно проверяются только ранее
действующие ID, исчезнувшие после законченной корректной активной выборки.
Ошибка/неполная выдача не является подтверждением архивирования.

Финансовый запрос уже читает `customer/index` по точному ID. Callback передаёт
его основные сведения в тот же механизм обновления без дополнительного
CRM-запроса. Для карточек с неотвеченными сообщениями действует существующее
30-минутное расписание. Остальные карточки показываются из постоянного
локального хранилища и при открытии обновляются через имеющуюся очередь.
Открытие чата не ждёт внешнего CRM-запроса.

## Имена, поиск и причины проверки

`customer_updates.refresh_contact` рассчитывает подпись по всем текущим
карточкам контакта. При согласованном новом ФИО обновляются contacts,
alfa_directory и поисковая строка. При противоречивых текущих представителях
сохраняется детерминированная существующая подпись, а причина проверки
рассчитывается `crm_review.cached_status`. Последняя обработанная карточка
не может произвольно переименовать общий контакт нескольких детей.

Изменение ФИО не создаёт постоянный needs_review. Причины вычисляются по
текущим данным; разрешившийся конфликт снимается, остальные сохраняются.
Ручная привязка разговора остаётся отдельным ограничением. Первое включение
исправляет старые подписи порциями по 100 контактов через `repair_labels`:
один локальный проход на опубликованный снимок, без повторного импорта CRM
или сообщений. Настройки порядка ребёнок/представитель не меняются.

## Преемственность и конкурентные ответы

Полная публикация передаёт в `project_directory` прежние карточки вместе с
контактами, учениками и основными контактными адресами. Уточнение имени при
неизменном подтверждённом адресе сохраняет локальные ID. Ранее разные контакты
не объединяются от того, что новые имена совпали. Смена адреса не позволяет
присоединиться к другой существующей семье. Новая карточка также не занимает
существующий контакт только по совпавшей подписи и телефону. Начальное
группирование нового справочника сохраняет прежний контракт, но само по себе
не доказывает идентичность MAX-аккаунтов.

Маркеры `crm.customer.observation.v1` хранятся в существующем outbox отдельно
для workspace/CRM-подключения/снимка/филиала/Customer ID. В них только время
начала чтения (в том числе по явно полученным полям), ревизия, источник и
версия настроек — без ФИО и телефонов. Наследованное из кэша поле не становится
свежим наблюдением из-за получения другого поля в частичном ответе.
Поздний результат старого запроса не перезаписывает более новое наблюдение
этой карточки. Время берётся из БД перед IO; возобновлённая карточка сохраняет
исходное время checkpoint. Проверки настроек, опубликованного run и аренды
сохраняются в вызывающих работниках.

Страницы явного полного импорта получают такие же маркеры. Перед публикацией
`carry_forward` переносит более новые точечные основные сведения из текущего
снимка, включая карточку, появившуюся после начала импорта. Более новая
страница полного импорта имеет преимущество. Сведения другого CRM-подключения
и недоступного филиала не переносятся. Балансы не подменяются этим механизмом.

## Сообщения и адресат

Совпадение Customer ID не доказывает единственного собеседника: у ученика
может быть несколько представителей. Явный MAX ID входящей записи сохраняет
приоритет; неизвестный ID не вычисляется из номера телефона. Перед POST
проверяются подготовленный адресат и подпись текущей маршрутизации каталога,
включая контактный адрес даже при известном MAX ID. Изменение данных до POST
откладывает отправку с повторной подготовкой существующей команды.

Перепривязка одной записи и объединение диалогов разделены. Метаданные
известной записи повторно проверяются `new_records`; выбранный адресат обязан
соответствовать спискам исходной записи и своей семейной проекции. Только
полная повторная обработка известного источника (`source_metadata_refresh`),
точные source ID/время и подтверждённая новая карточка могут переместить эту
запись. Сохраняются её локальный ID, текст и время.

Объединение остальной истории дополнительно проверяет `history_proven`:
другие старые входящие должны иметь тот же явный MAX ID. При неизвестном
аккаунте разрешено объединить только копии проверяемой записи; другая старая
история остаётся в своём разговоре. Разные явные аккаунты блокируют объединение.
Проверки текущего каталога, телефонов, namespace/подключения и ручных связей
сохраняются. Стандартное подтверждение совместных получателей одной исходной
записи остаётся отдельным механизмом `alfa_shared_parent`.

Переименование/перевод статуса не обновляют дату диалога, время ожидания,
прочтение или обработку. При изменении состава разговора имеющиеся механизмы
пересчитывают очередь по реальным сообщениям и сохраняют происхождение копий.
Старые failed-команды не переотправляются автоматически; неизвестный результат
уже начатого POST не повторяется.

## Проверка и выпуск

`scripts/diagnose_max_recipients.py` делает только GET-проверку последних двух
диалогов с ошибкой адресата. После ожидания браузера заново читает выбранную
карточку. `stored_incoming` — сохранённая связь, `branch/customer` — текущий
адрес отправки, `catalog` — статусы карточек и маркер наблюдения. Данные
персональных полей и реальные MAX ID в отчёт не выводятся.

Ожидание браузера ограничено 210 секундами, чтение — 120: это укладывается в
360-секундный лимит обёртки и позволяет дождаться остатка обычной аренды.
Чужая аренда не сбрасывается. Timeout означает, что проверка не началась,
а не что CRM разлогинилась. Статический SSH support-скрипт обновляется его
установщиком; обычная замена контейнера не заменяет support-файлы на хосте.

Сам механизм обновления основных сведений не требует миграции схемы.
Дополнение [«Выбор действующей карточки»](active-client-display.md) использует
отдельную миграцию `0025_customer_phone_search` для поиска по всем телефонам.
Выпуск — PR и существующий
`ramessenger-local-build.service`/таймер, без GitHub Actions. Автоматические
проверки и build/ready не заменяют подтверждение рабочей CRM-привязки,
сохранности истории после перезагрузки и обычной отправки оператором.
