# Проверка MAX и обычный бэкап трёх контейнеров

## Исправление временных файлов SQLite, 31 октября 2026

Старая реализация использовала контекстный менеджер `sqlite3.Connection`
как закрытие соединения. Он только завершает транзакцию: соединение со снимком
оставалось открытым. После копирования исходной WAL-базы проверка создавала
пустой WAL и SHM; `finish()` включал их в manifest. При выходе процесса SQLite
удаляла временные файлы, и повторная проверка находила несовпадение.

Теперь оба соединения закрываются явно. Целевой снимок переводится в DELETE
до проверки и закрытия; исходная база остаётся в своём режиме. Финализация
отказывается включать SQLite WAL/SHM/journal в комплект. Регрессия проверяет
копирование настоящей активной WAL-базы и чтение после закрытия соединений.

Для уже созданного комплекта есть отдельный узкий инструмент:

```bash
python3 scripts/seal_sqlite_backup.py --backup /путь/к/исходному-комплекту --output /путь/к/новому-комплекту
```

Он принимает только известный дефект: manifest содержит пустой WAL с SHA256
пустого файла и SHM размером 32768. Непустой WAL, rollback journal, повреждение
любого реального payload, несовпадение исходных SHA256SUMS или ошибка SQLite
останавливают операцию. SQLite проверяется в `mode=ro&immutable=1`, включая
integrity, внешние ключи и числа строк. Исходные данные и manifest не меняются.

Новый соседний каталог содержит жёсткие ссылки на проверенные payload,
исходные manifest/SHA256SUMS и отдельный отчёт о восстановлении комплекта.
Это проверенное представление тех же файлов, **не вторая физическая копия**.
Дата бэкапа и свидетельства прежнего восстановления PostgreSQL сохраняются;
восстановление PostgreSQL повторно не объявляется выполненным. Новый комплект
проходит обычный строгий `verify_integrity()` без исключений и может быть
передан штатному подготовщику выпуска. Исходник не удаляют до отдельной
внешней копии. При удалении одного имени жёсткой ссылки второе остаётся,
но изменение общих payload изменит оба представления — их нельзя редактировать.

Инструмент не меняет guard, контейнеры или базу приложения. Использует те же
backup/deploy locks, не удаляет блокировки и не запускает второй deploy owner.

а затем контролируемого обновления обоих образов до

ошибок сессии не было, все 20 принятых за сутки команд имели сохранённые сообщения.
Три старые ошибки `recipient_missing` требуют отдельной проверки адресатов;
это не разрешение автоматически повторять отправки. Одна отмена SQL `57014`
при сохранении страницы восстановилась повтором; конкретный запрос и причина
отмены по одной строке worker-журнала не установлены.

Новая копия `/var/backups/ramessenger/20261030T192753Z-4f861219aefa` получила
`state=complete` до обновления worker. Этот скрипт устанавливает такой статус
после изолированного восстановления БД. Скачивание копии вне VPS и полное
восстановление приложения не подтверждены.

`scripts/full_backup_split.py` — обслуживающий скрипт, не второй deploy owner.
Он не обновляет приложение, Compose, pin MAX, схему, guard или чужие проекты;
не выполняет отправок, не запускает браузер, не очищает аренды и очереди.
GitHub Actions не используются. Скрипт запускается root из точно проверенной версии.

## Диагностика

```bash
python3 scripts/full_backup_split.py --audit
```

Проверяет роли/health API и MAX, состояние PostgreSQL, точное соответствие
MAX image ID и `.env` подготовленному переходу, хэш установленной policy и
совпадение её schema revision с базой. Показывает состояние native-сессий,
время последней синхронизации, импортированные записи входящих/исходящих
за сутки, состояния исходящих команд и число ожидающих больше пяти минут.
Отдельная проблема — принятые команды, у которых нет сохранённого сообщения.
Успешное чтение истории старше пяти минут при активной сессии также считается
проблемой, даже если контейнер `healthy`. Выводятся сохранённая фаза работы,
история очереди и агрегированные коды/времена неудачных отправок за сутки.
Текущая ошибка видна и после недавнего успешного чтения. Отсутствие первого
успешного чтения и ожидание отправок больше пяти минут также дают проблему.
При обрыве readiness во время замены API отчёт сохраняет DB-свидетельства и
показывает `api_ready=false`; это не сбой ранее завершённого бэкапа.
Пароли, cookies, тексты, ФИО и телефоны в отчёт не попадают.

Запросы к рабочей БД выполняются внутри `BEGIN READ ONLY` с statement timeout.
Код возврата 2 означает найденные проблемы; это не команда повторить отправку.
Занятость браузера, неопределённая доставка и неактивная сессия не исправляются
из диагностического скрипта. Нужно разобрать отчёт, сохранив исходные send intents.

Это чтение сохранённых свидетельств, а не проверка всей цепочки доставки.
Для приёмки реального обмена сопоставить обычные сообщения оператора/клиента
с журналом AlfaCRM. Искусственные сообщения клиентам автоматически не отправляются.
Для проверки независимости обновлений сохранить `id` и `started_at` MAX из
отчёта до/после следующего штатного API-релиза: они должны остаться прежними.
Ради этого теста скрипт не перезапускает ни API, ни MAX.

## Разбор задержек и старых ошибок отправки

`scripts/max_runtime_diagnostics.py` запускается на VPS рядом с актуальным
`full_backup_split.py`. Это чтение, не deploy controller и не CRM-проверка.

```bash
python3 scripts/max_runtime_diagnostics.py --since 2026-10-30T19:50:35Z
```

Отчёт содержит последние 20 неудачных native-команд за 30 дней: command ID,
conversation ID, contact ID, Customer ID/филиал последнего сохранённого
входящего, опубликованные CRM-карточки и текущие членства в группах. Сохранённая
display projection дана как подсказка; её совпадение с публикацией/настройками
не заменяет проверки полной подписи и не разрешает отправку выбранному клиенту.
Исторический адресат самой неудачной попытки может отличаться от текущих данных.

В DB-снимке видны возраст запросов/транзакций, ожидания и число блокирующих
backend, отпечатки запросов и статистика основных таблиц. Сырые SQL, параметры
и содержимое `payload` не выводятся. Настроенный timeout читается из окружения
MAX-контейнера: это не измерение настроек уже открытой DB-сессии.

Читаются только последние 2000 строк PostgreSQL и MAX за указанное окно,
не более 2 MiB и 20 секунд на контейнер. Сохраняются в отчёт только разрешённые
поля: время, PID, SQLSTATE/фаза и известная причина отмены. При наличии связанной
`STATEMENT` того же PostgreSQL PID добавляются её хэш, вид операции и имена
из ограниченного списка таблиц. Эти поля — диагностические признаки, не полный
план запроса. Отмена из PostgreSQL не приписывается MAX только по совпадению
времени; нужны отдельное сопоставление и, при необходимости, план запроса на
изолированной копии. `truncated=true`/`read_ok=false` обозначают неполный лог.
Отсутствие события в выборке не означает, что ошибки не было. Таймауты,
логирование PostgreSQL, очереди и аренды скрипт не меняет.

Для проверки обычного API-релиза перед ним записать небольшой снимок:

```bash
python3 scripts/max_runtime_diagnostics.py --record-baseline /opt/center-messenger-github/support/max-before-api-release.json
```

После завершения штатного `ramessenger-local-build.service`:

```bash
python3 scripts/max_runtime_diagnostics.py --compare-baseline /opt/center-messenger-github/support/max-before-api-release.json
```

Нужны `max_unchanged=true`, `api_replaced=true` и дальнейшее успешное чтение
истории. Сравниваются container ID, image ID/tag, start time и restart count MAX.
Имеющийся baseline не перезаписывается, файл создаётся с правами 0600.
Для следующей проверки выбрать новое имя. Если worker был отдельно и намеренно
обновлён, прежний baseline ожидаемо не совпадёт; это не повод откатывать БД.
`--expected-worker-id <полный Docker ID>` дополнительно проверяет известный
оператору экземпляр. Никаких отправок или запросов к CRM для этой проверки нет.

## Запуск резервного копирования

```bash
python3 scripts/full_backup_split.py --start
tail -n 40 /var/log/ramessenger-full-backup.log
```

Создаёт transient systemd service и немедленно возвращает управление WinSCP.
Ни GitHub credentials, ни отдельный ключ шифрования фоновому заданию не нужны.
Копия обычная, без шифрования, хранится в закрытом каталоге
`/var/backups/ramessenger/<UTC-время>-<идентификатор>` с mode 0700, файлы — 0600.
В ней есть рабочие секреты и персональные данные: хранить её в закрытом месте.

Очередность:

1. Захват `.full-backup.lock` и существующего проектного `.deploy.lock`.
   Если идёт другой бэкап/деплой, скрипт завершается без остановки приложений.
   Таймеры не отключаются; попытки деплоя во время бэкапа могут сообщать о занятом
   lock и продолжатся обычным таймером. Файлы lock не удаляются.
2. Инвентаризация ровно API/MAX/DB, проверка read-only runtime и известных mounts,
   отчёт диагностики. Неактивная CRM-сессия не мешает сохранить уже имеющиеся данные.
3. Проверка места: несжатые проектные файлы, уникальные образы, дампы/восстановление
   и 3 GiB резерва. При недостатке копия не начинается; старые архивы не удаляются.
   Архивирование также прерывается, если свободное место опустилось ниже резерва.
4. Архив всех обнаруженных `/opt/center-messenger*`, mounted secrets, внешней
   защиты `/etc/ramessenger-max-guard`, systemd/drop-ins, proxy/SSL и зависимостей.
   Поддерживаются дополнительные зависимости nginx и unit-файлов.
   Живая SQLite support-очередь сохраняется online backup API отдельно от WAL/SHM.
   Временные журналы, события support-аудита и `__pycache__` перечислены как
   исключения: они не являются входными данными восстановления.
5. Сохранение точных образов API, закреплённого MAX и PostgreSQL. Общие layers
   Docker экспортирует один раз; исходные ссылки и IDs входят в метаданные.
6. Сохранение глобальных PostgreSQL ролей, затем всех доступных нетиповых БД.
   Для каждой БД удерживается `REPEATABLE READ READ ONLY` snapshot:
   `pg_dump --snapshot` и контроль всех пользовательских таблиц используют его.
   Новые сообщения продолжают поступать; у разных БД могут быть разные времена.
   Бизнес-данные мессенджера находятся в одной `center_messenger`.
7. Проверка TOC и полного чтения дампа через **прямой stdin файла**. Конвейера
   `cat | pg_restore --list`, вызывавшего SIGPIPE и ложный сбой, нет.
8. Создание PostgreSQL того же image ID в отдельном контейнере с уникальным
   labelled volume, `network=none`, без портов и production mounts.
   Восстановление ролей и всех дампов с владельцами/ACL и `--exit-on-error`.
   Сравнение числа строк каждой пользовательской таблицы и версии схемы.
9. Удаление только собственных проверочных контейнера/тома по совпавшему label.
   При чужом label удаление блокируется. Ни один рабочий том не удаляется.
10. Запись manifest, SHA256SUMS, recovery metadata, инструкции и копии скрипта;
    повторное чтение SHA-256. Только затем `BACKUP_COMPLETE`.

API/MAX/PostgreSQL продолжают работать весь процесс. Логическая копия заменяет
небезопасное копирование живого PGDATA. Физический base backup здесь не создаётся.
Если появятся writable mounts приложения, дополнительные tablespaces или другой
layout PostgreSQL, скрипт останавливается для отдельного плана согласованности.

## Проверка результата

```bash
python3 scripts/full_backup_split.py --verify /var/backups/ramessenger/ИМЯ_КОПИИ
```

Нужны `BACKUP_COMPLETE`, `state=complete`, `restore_verified=true` у каждой БД
в manifest и `BACKUP_INTEGRITY_OK`. Один `SAVED ...` не означает завершение.
Скопировать всю папку с сервера, затем повторить проверку на полученной копии.
Копия на том же диске не защищает от потери VPS.

Реальное восстановление БД в изолированном Docker выполняется при каждом запуске.
Локальные unit-тесты скрипта не заменяют эту проверку на VPS. Проверка полного
запуска приложения, RLS, SSL/DNS и внешней сессии CRM в окружении восстановления
остаётся отдельной приёмкой. Готовая инструкция `RESTORE.txt` явно запрещает
накладывать файлы на работающую систему и включать второй production MAX.
