# Точечная загрузка клиентов и расчёт «Сводки»

## Что исправлено

Новое обращение с ещё неизвестным ID AlfaCRM сохранялось, но отсеивалось из
`chat-updates` до появления карточки в полном справочнике. Теперь оно сразу
попадает в список, счётчики и обновления. Сохранение сообщения атомарно ставит
фоновую задачу точечного получения клиента. Задача общая для одного CRM ID
в данном подключении и рабочем пространстве, включая наблюдения в филиалах.

Работник запрашивает только конкретный ID, сначала среди неархивных карточек,
затем среди архивных. Ответ с чужим ID, несколькими карточками или неподтверждённой
пагинацией не применяется. Ошибки доступа, ключа, временные ошибки и отсутствие
карточки различаются. Повторы ограничены задержкой; смена настроек снимает
ожидание. После перезапуска задачи продолжаются; ранее сохранённые неизвестные
ID подбираются ограниченными порциями из нашей БД.

При публикации проверяются настройки, CRM connection, версия справочника,
доступность филиала и аренда задачи. Ручные связи не заменяются. Используется
существующая проверенная привязка по CRM ID и механизм объединения зеркал;
совпадения телефонов/имён не являются основанием привязки. Тексты, ID сообщений,
время и исходные записи сохраняются. После привязки выпускаются изменения
даже для уже пройденного курсора, без нового сигнала входящего. Существующие
проверки получателя непосредственно перед отправкой сохраняются.

В правой карточке неизвестного клиента отображаются ID, причина ожидания и
время следующей проверки. Чтение списка и истории по-прежнему работает из БД.
Подробности финансов/занятий загружаются обычным кэшем карточек.

«Сводка» уже использовала только нашу БД. Для времени ответа теперь читается
хронология текущего периода и одно предшествующее значимое событие каждого
диалога с ответами. Исключены повторные коррелированные поиски для каждого
исходящего. Учитывается первый подтверждённый ответ человека; повторные ответы,
автоуведомления, неуспешные отправки и скрытые дубли не искажают время реакции.
При совпадении времени соблюдается общий порядок сообщений по ID источника.

## Проверки

- SQL-регрессии точечной загрузки: новый лид, архив, неизвестный ID, неподдержанный
  фильтр, повторные сообщения/филиалы, уведомления, атомарный откат, потеря аренды,
  смена настроек/справочника/доступа к филиалу, ручная привязка, восстановление после
  изменения ключа и недопущение второго исполнителя.
- Метрики: границы календарных дней/DST, начало ожидания до периода, уже отвеченное
  обращение до периода, одинаковое время событий, автоуведомления и неудачные ответы.
- Интерфейс: объяснение состояния неизвестной карточки и обновление причины/срока.
- CI: полный набор Python/UI, PostgreSQL 16, сборка Docker, проверка изоляции
  отправителя внутри образа, граф миграций; отдельный короткий SQL-замер на
  синтетической истории 60 001 сообщений под ролью `cm_app` с RLS.

Короткий замер SQL не измеряет HTTP, ожидание пула API, многопользовательскую
работу и фоновую синхронизацию. Это **не** 30-минутная приёмка из ТЗ.

## Установка и проверка рабочего сервера

Миграция схемы, сброс курсоров и повторный импорт сообщений не нужны.

```bash
systemctl start ramessenger-local-build.service &&
docker inspect --format '{{.Config.Image}}' center-messenger-api-1 &&
curl -fsS http://127.0.0.1:8100/health/ready
```

Пассивные сведения о настройках PostgreSQL и агрегированном ожидании блокировок:

```bash
docker exec center-messenger-api-1 /opt/venv/bin/python -m center_messenger.summary_audit
```

Один реальный расчёт с временем каждого SQL-этапа, без текстов переписки и ФИО:

```bash
docker exec center-messenger-api-1 /opt/venv/bin/python -m center_messenger.summary_audit --calculate
```

Команда использует отдельный пул процесса диагностики, а не пул работающего API.
При 503 также нужны строки `Database operation failed`, `Slow summary calculation`
и `Slow API read` из журнала API за момент запроса. Код `57014` означает отменённый
запрос; сам по себе не доказывает `statement_timeout`. Пассивная команда не
запускает расчёты; `--calculate` читает реальные данные один раз, ничего не меняет
и не обращается к AlphaCRM. При недостатке прав/отказе БД выдаёт безопасный тип
ошибки и SQLSTATE без SQL, параметров или текста драйвера.

## Граница завершённости ТЗ

Этап 3 реализован этим выпуском. Этап 0.1 пока нельзя считать принятым: причина
наблюдавшейся 503 на VPS ещё не подтверждена диагностикой, нет сопоставимого
30-минутного испытания с фоновыми задачами и замеров до/после. Постоянный снимок
«Сводки» добавляется по результатам измерений, если SQL остаётся тяжёлым.
Остальные ранее незакрытые этапы 0, 4–7 этим выпуском не объявляются выполненными.

Откат на предыдущий образ не удаляет данные; старый работник игнорирует новые
задачи точечной загрузки. Новые карточки и привязки остаются в совместимой схеме.
