# Проверка связей клиентов, групп, занятий и абонементов

`build: 7cd1078d7a84` и `schema: 0015_family_refresh_tiers`. `/health/ready`

## Исправленные ошибки

1. Полное совпадение ФИО и даты рождения могло объединять разные Customer ID
   в одного ребёнка. Теперь идентичность определяется ID внутри подключения CRM.
   Наблюдения одного ID в разных филиалах принадлежат одному ребёнку. Исправления
   анкетных данных сохраняют существующий однозначный локальный ID.
2. Исторические объединения разделяет возобновляемая фоновая проверка по 100 ID.
   Для неоднозначного старого локального ID выбирается один прежний владелец;
   остальные получают отдельные привязки. Ручные связи сохраняются, затронутая
   семья отмечается для проверки. Обработка идёт в опубликованном справочнике,
   история сообщений и финансовые факты остаются привязанными к исходным ID.
3. Удалённый абонемент мог оставаться из старого филиального кэша, даже когда
   свежий полный список этого Customer ID его уже не содержал. Теперь состав
   покупок определяется последним полным списком клиента, включая пустой список.
   Равносвежие противоречивые списки требуют проверки и не доказывают баланс
   покупки или её связь с филиалом.
4. Дата занятия группы могла браться из старой зеркальной копии после переноса.
   Теперь прежде вычисления дат выбирается последняя непротиворечивая версия
   занятия. Более свежая полная проверка окна фактического филиала может
   подтвердить удаление. Проверка недавнего периода не обновляет дату наблюдения
   сохранённых старых занятий; границы окна учитывают местную дату организации.
5. Современное участие в группе могло ошибочно подтверждать старое занятие до
   даты вступления. Для такого подтверждения теперь требуется период CGI,
   покрывающий дату занятия. Чужой Customer ID и равносвежие противоречивые
   сведения не выставляют дату группы или филиал абонемента.
6. Счётчик групп различает пару «филиал + ID группы». Лёгкая сверка профиля
   сохраняет дату рождения и идентичность ребёнка при появлении того же ID
   в другом филиале, в том числе без необязательного `branch_ids`.

## Обновление действующих групп

Отдельные долговечные задания `crm.customer.groups` читают документированный
`cgi/customer?customer_id=…` и проверяют метаданные групп через `group/index`.
Сохраняются ID клиента, группы, записи CGI и даты участия. По доступным полям
CRM отбрасываются наблюдения чужого филиала и архивные/удалённые группы.

- Автоматически сверяются действующие клиенты с периодом 6 часов после
  последнего успешного сохранения. Архивные клиенты требуют явного открытия.
- Это лёгкая сверка связей. Финансовая карточка клиента, не ожидающего ответа,
  по-прежнему готовится при открытии; CGI не запускает её фоновое чтение.
- Приоритет имеют запросы оператора и очередь финансов/занятий. Частота
  фактического выполнения зависит от очереди и доступности CRM.
- Метаданные групп переиспользуются в ограниченном кэше на 30 минут, отдельно
  для каждого центра, подключения и версии настроек. CGI клиента читается заново.
- Связи заменяются одной транзакцией только для выбранных клиента и филиала.
  Ошибка или конфликт CGI ID сохраняют предыдущие сведения и срок повторения.
- Проверяются версия настроек, опубликованная копия, привязка клиента и аренда.
  Принудительный запрос во время чтения остаётся в очереди после завершения.

В подключении видны операция, имя, имя ребёнка, Customer ID и филиал. Прогресс
сверки групп действующих клиентов показывается отдельно от готовности карточек,
ожидающих ответа. Один Customer ID считается один раз; готовность требует
проверки всех доступных наблюдений этого клиента. Карточка показывает дату
проверки групп, в том числе последнюю успешную дату при ошибке.

## Проверки и установка

Проверены чистые функции идентичности, полные/пустые списки покупок, переносы,
отмены и конфликтующие зеркала занятий; документированные ответы CGI; замена
только выбранного клиента/филиала; самостоятельное обновление групп без чтения
финансов; шестичасовой срок; архивные клиенты; ошибки, смена настроек и запросы
во время чтения; разделение исторических привязок с сохранением сообщений
и ручных связей; счётчики и отображение на компьютере и телефоне.

Успешны 283 серверных теста и 94 проверки интерфейса. Браузерные проверки
карточки выполнены при ширине 1440 и 390 px; загрузчика — 1440, 390 и 320 px,
в светлой и тёмной темах, без ошибок и горизонтального переполнения.
Тесты используют изолированную базу и синтетические данные. Два существующих
теста параллельных транзакций требуют обычный PostgreSQL и пропускаются в PGlite.
Публичная проверка установленной версии не является аудитом частных данных CRM.

Дополнительная миграция схемы для этого выпуска не требуется. Штатная установка:

```bash
systemctl start ramessenger-local-build.service &&
docker inspect --format '{{.Config.Image}}' center-messenger-api-1
```

После запуска версия должна совпадать с опубликованным коммитом `main`.
Затем обновить страницу: разделение прежних ошибочных привязок и проверка групп
начнутся на сервере; их завершение зависит от объёма исходных данных и очереди.
