# Диагностика после восстановления native MAX

## Изменения

- Исправлен host-аудит: текущая ошибка не скрывается последним успехом,
  очередь старше пяти минут и отсутствие первого чтения дают проблему.
- Обрыв readiness при перезапуске API сохраняет DB/runtime-свидетельства;
  ошибка команды аудита не подписывается как сбой резервного копирования.
- Добавлен `scripts/max_runtime_diagnostics.py`: read-only сведения о последних
  неудачных командах и связанных точных CRM ID, DB-ожиданиях, безопасных
  признаках отмены запросов из ограниченной выборки DB/MAX-журналов.
- Добавлены запись и сравнение runtime-baseline, позволяющие проверить, что
  обычный API-релиз сохранил закреплённый worker и история продолжила чтение.

## Выпуск и ограничения

Контур MAX, policy, Compose, зависимости, схема и действующий worker не
изменены. Обычный API-выпуск выполняет прежний deploy owner без GitHub Actions.
Host-скрипты нужно отдельно установить из точной проверенной версии: обновление
API не заменяет `/opt/center-messenger-github/support/*.py`.

SQL `57014` означает отмену; её точная причина/запрос и нынешние адресаты
трёх старых `recipient_missing` требуют нового серверного отчёта. Диагностика
не повторяет сообщения, не выбирает нового адресата и не обращается к CRM.
Отсутствие сырого текста не даёт автоматически сопоставить неудачную команду
с уже отправленной вне мессенджера: эту сверку выполняют отдельно.

Проверка полного запуска приложения из бэкапа и наличие внешней копии не
подтверждаются этим выпуском. Старые архивы не удаляются.

## Проверки

91 тест прошёл локально: 31 полного бэкапа/аудита, 12 диагностики,
27 защиты выпуска и 21 перехода/обновления worker. Оба диагностических SQL
дополнительно проверены парсером PostgreSQL; это не выполнение на рабочей БД.
Проверены реальные bounded pipe-чтения stdout/stderr, отсутствие SQL/переписки
в отчёте, отсутствие перезаписи baseline, изменение каждого признака worker,
обычная замена только API, API readiness во время перезапуска и ошибки очереди.
Тесты SQL на реальной production-БД и снимок после API-выпуска выполняются
только на VPS; локальные unit-тесты не подменяют такую приёмку.
