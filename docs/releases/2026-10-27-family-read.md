# Чтение карточки без пересчёта переписки

В рабочем журнале зафиксированы успешные GET `/chats/{conversation_id}/family`
за 1516 и 1442 мс. Строк об ошибке «Сводки» или SQL в предоставленном фрагменте
нет. Общее время запроса включает авторизацию, ожидание БД и подготовку ответа;
по этим двум строкам нельзя выделить длительность отдельного этапа.

Проверка кода выявила лишнюю работу: маршрут карточки вызывал полный
`ChatReader._conversation`, пересчитывая состояние всей истории сообщений,
хотя ему нужны только ID диалога и связь с CRM-контактом. Это происходило до
чтения уже подготовленной карточки и на каждом её повторном запросе.

Теперь отдельный ограниченный запрос получает сохранённую связь. Он проверяет
рабочее пространство, тип диалога, наличие настройки канала и разрешение на
чтение чатов. Старый ID объединённого диалога переходит к каноническому; ручная
привязка сохраняется. Повторная авторизация и проверка принадлежности контакта
в `DirectoryReader.prepare` остаются. Для этого чтения не нужны сообщения,
счётчики, их проекция или курсор изменений. Обновление по кнопке также использует
короткое определение контакта и сохраняет проверку прав администратора.

Сам GET не выполняет HTTP-запросы AlphaCRM: сведения читаются из нашей БД,
при необходимости ставится фоновая задача обновления карточки. Расписания,
содержимое карточки и правила неотвеченных сообщений этим исправлением не меняются.

Если этап длится от 250 мс, журнал с прежним префиксом `Slow API read` содержит
`stage=family.resolve` (поиск связи и доступ) либо `stage=family.prepare`
(подготовка карточки, кэш и постановка фоновых задач). Полное время GET по-прежнему
пишется при длительности от 1000 мс. В записи нет ID клиентов, имён, SQL или секретов.

Регрессии проверяют отсутствие запросов к истории даже при отсутствующей
проекции очереди, канонический/ручной выбор, запрет чужого рабочего пространства,
группового диалога, отсутствующего подключения и доступа без членства.
Прежняя ошибка 503 в «Сводке» не объявляется устранённой по этим двум логам.

После установки открыть те же карточки и посмотреть журнал:

```bash
docker logs --since 5m center-messenger-api-1 2>&1 |
grep -E 'Database operation failed|Slow summary calculation|Slow API read'
```

Отсутствие медленных записей означает только, что в этом интервале не был
зафиксирован запрос/этап выше порога; оно не доказывает, что нужную карточку
открывали. Фактическую задержку после изменения нужно проверить на сервере.
Миграция схемы и сброс истории не требуются.
