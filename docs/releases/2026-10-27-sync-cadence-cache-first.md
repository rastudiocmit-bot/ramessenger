# Этап 5: периодичность загрузки и карточка из кэша

При открытии правой карточки сначала показывается последний целостный снимок
из PostgreSQL на постоянном диске сервера. Затем отдельный запрос ставит
просроченные разделы в очередь. Оба запроса читают нашу БД и не ждут AlfaCRM.
Снимок остаётся видимым при обновлении, сетевой ошибке, смене оператора и после
перезапуска приложения. Пустой кэш не выдаётся за нулевой баланс.

Стрелка обновления вращается во время ручного запроса и работы фоновых задач.
Индикатор виден сотруднику, даже если у него нет права принудительного обновления;
право отправить команду остаётся прежним. При блокировке ключа или ожидании
повтора анимация прекращается, сохранённые данные и причина остаются доступны.
Открытая карточка опрашивает готовые данные, а не запускает повторные запросы CRM.

## Расписание

| Данные | Правило |
|---|---|
| Старая переписка | Один импорт; незавершённая страница продолжается по курсору |
| Новые сообщения в обе стороны | Серверный опрос с целевым интервалом 15 секунд на журнал, с учётом очереди и ограничений CRM |
| Действующие клиенты | Раз в 6 часов; исчезнувший действующий ID проверяется точечно, включая архив |
| Баланс и абонементы семьи с `needs_reply` | По сроку 30 минут |
| Последние 30 дней и будущие 90 дней занятий при `needs_reply` | По сроку 30 минут |
| Год занятий при `needs_reply` | 24 часа; отдельная задача, это не архив сообщений |
| Группы действующих клиентов | 6 часов |
| Остальные подробные карточки | При открытии, с теми же сроками пригодности сохранённых разделов |
| Филиалы и названия статусов | Лёгкая сверка раз в 6 часов |

Интервалы — сроки постановки задач, а не обещание завершения при недоступной CRM.
Показывается фактическое время чтения. Старый таймер полного справочника после
первой публикации отключается независимо от подключения MAX. Явно запущенный
полный импорт разрешён; обычная шестичасовая сверка не читает архив массово.

`catalog_review.py` отдельно обновляет список филиалов, `study-status` и
`lead-status`. Каждая операция имеет собственные страницы, аренду и повтор.
Список заменяется только после проверки всех страниц. Лимит хода — три новых
запроса, контрольная точка ограничена 8 МиБ. При сетевом сбое хорошие страницы
не запрашиваются заново. 401 ждёт новой версии реквизитов; 403 ограничен
операцией филиала с повторной проверкой через 6 часов; 429 соблюдает общий бюджет
и Retry-After. Эти задачи используют
общие ограничения API CRM из `card_jobs.py`, но не изменяют сессии MAX/сотрудников.

Новый филиал получает только собственные статусы, проверку действующих клиентов
и два новых журнала сообщений. Завершённые журналы и курсоры остальных филиалов
сохраняются. Дополнительная проверка нового филиала не переносит очередной срок
шестичасовой проверки прежних филиалов. Отказ одного филиала не блокирует
проверку клиентов остальных; он сохраняется отдельно в `branch_errors`.

## Полнота и отсутствие повторных запросов

Догрузка новых сообщений хранит ID предыдущей свежей страницы как границу.
Одиночный ранее сохранённый ID из другой части журнала не завершает догрузку.
Если первый ID границы удалён в CRM, остальные ID той же страницы позволяют
найти перекрытие. При новом наплыве записей во время догрузки сохраняется
отдельная следующая граница. Старый курсор импорта не сбрасывается.

Входящие архивного клиента сохраняются по тем же правилам. Повтор одного ID
не создаёт сообщение повторно; разные ID с одинаковым текстом остаются разными
сообщениями. Разница общего числа строк и уникальных ID не запускает архив
заново. Проверка полноты по-прежнему различает повторяющиеся строки источника,
ограниченное доказательство и конкретные отсутствующие ID. Изменяемая страничная
выдача CRM не даёт транзакционного снимка всей истории.

Годовая задача использует свежее полное получасовое покрытие того же локального
дня: читает только дни от −365 до −31, не повторяет последние 30 дней и будущие
90 дней. Если такого покрытия нет или оно устарело, выполняется полный запрос.
Границы фиксируются в контрольной точке, а `lessons_history_through` хранит
реальный последний день годовой проверки. Старые целостные данные сохраняются
до завершения раздела. Долгая годовая задача не отменяет более свежий перенос
или отмену занятия, опубликованные получасовой задачей во время её работы.

## Установка и проверка

Миграция `0020_lesson_history_coverage` добавляет nullable-границу покрытия и
инвалидацию представления карточки при изменении названий статусов. Она не удаляет
сообщения и не обнуляет кэш. Прежний образ совместим с добавленной колонкой;
при откате его старый алгоритм запросов вернётся. Удалять колонку при обычном
откате образа не требуется.

```bash
systemctl start ramessenger-local-build.service &&
docker inspect --format '{{.Config.Image}}' center-messenger-api-1 &&
curl -fsS http://127.0.0.1:8100/health/ready
```

Пассивная диагностика без запросов в CRM:

```bash
docker exec center-messenger-api-1 /opt/venv/bin/python -m center_messenger.history_audit
```

В ней добавлены `catalog_review` и `active_review`: срок следующей проверки,
состояние и причина ожидания; промежуточные страницы не выводятся. Остальные
счётчики истории сохраняют прежний смысл. Признак недостаточного доказательства
полноты не означает, что база была очищена.

Приёмка интерфейса: открыть уже загруженную карточку, нажать обновление и
убедиться, что баланс/абонементы остаются видимыми, стрелка вращается, по завершении
меняются дата/данные без скачка прокрутки. При недоступной CRM остаётся предыдущий
снимок. Перезагрузка вкладки не должна запускать повторный архив.

Автоматические регрессии покрывают сроки, добавление филиала, отказ филиала,
401, смену настроек/аренды, продолжение страниц, архивного клиента, идентичные
тексты с разными ID, границы занятий и сохранение карточки во время обновления.
Результаты CI указываются в PR. Скорость и доступность рабочего VPS требуют
проверки после установки; прежняя HTTP 503 в «Сводке» и этапы 6/7 этим не закрыты.
