# Клиенты АльфаCRM — версия 0.4.0

## Включение

Владелец или администратор открывает «Клиенты» и нажимает «Загрузить из CRM».
Используется уже настроенное подключение; перечислять филиалы вручную не нужно.
До первого нажатия миграция сама не начинает импорт персональных данных.

Флажок «Автоматически» и интервал применяются при запуске. По умолчанию — каждые
30 минут после завершения предыдущей загрузки; минимум 15 минут. Кнопка остановки
отменяет текущую загрузку и отключает расписание. Повторный запуск во время работы
возвращает то же задание. Выход из кабинета и закрытие браузера работу не отменяют.
Изменение подключения, отключение CRM или отзыв прав инициатора останавливают её.

Нужно обновление API-контейнера, миграция 0004 и CM_CRM_SYNC_WORKER=true;
Compose включает worker внутри единственного API-контейнера. Отдельный контейнер
пока не требуется. Установленный контроллер автодеплоя поддерживает этот выпуск.
PostgreSQL, его том и порт, Nginx и приложение сайта студии не меняются.

## Что загружается

Из всех доступных активных филиалов последовательно получаются:

- справочники статусов обучения и лидов;
- клиенты и лиды: customer/index с is_study=2, отдельно removed=0 и removed=2;
- активные группы: group/index с removed=0;
- периоды участия учеников в каждой группе: cgi/index?group_id=ID.

Используется документированный v2api, без чтения HTML карточек. Правильная
пагинация проверяет total; короткая страница сама по себе не завершает загрузку.
Одна итерация worker сохраняет страницу, курсор и счётчики в PostgreSQL. После
перезапуска процесс продолжает с последней зафиксированной страницы. Действует
общий ограничитель по адресу CRM, кэш авторизации, повтор 401 после обновления
токена, задержки при 429/временных сетевых ошибках. Удалённые из доступных филиалов
карточки исчезают из следующей опубликованной копии, история не удаляется.

Сохраняются ФИО ребёнка, ФИО плательщика (legal_name), дата рождения для сопоставления,
телефоны, email, статусы и связи с филиалами/группами. Адреса, комментарии и другие
неиспользуемые поля CRM не копируются. Актуальность группы определяется b_date/e_date
по дате часового пояса организации. Истёкшие и будущие периоды не выводятся.
Ссылки CGI на отсутствующие карточки учитываются отдельным счётчиком; фиктивные
дети на их основе не создаются.

Контракты: [API АльфаCRM](https://alfacrm.pro/usefull/integrations/integration/api),
[практическая схема интеграции](https://alfacrm.pro/usefull/knowledge/rekomendacii-po-rabote-s-sistemoj/v2api-prakticheskaya-skhema-integracii).

## Один контакт и несколько детей

| Случай | Результат |
| --- | --- |
| Одинаковый customer ID в нескольких филиалах | Один ребёнок, несколько ссылок на CRM-карточку |
| Разные дети с одинаковым основным телефоном родителя | Один контакт со списком детей |
| Разные customer ID, одинаковые полное ФИО ребёнка и непустая дата рождения внутри семьи | Один ребёнок с исходными карточками |
| Совпадает только имя или фамилия | Автоматического объединения нет |
| Один основной телефон, разные непустые ФИО плательщиков | Раздельные контакты с отметкой «Уточнить контакт» |
| Нет телефона, есть email | Основной email используется аналогично телефону |
| Нет телефона и email | Отдельный контакт исходной карточки |
| В нескольких карточках общий дополнительный номер | Он не склеивает семьи цепочкой |

Телефон приводится к международному формату: российские 8XXXXXXXXXX и
+7XXXXXXXXXX совпадают. Пробелы/скобки/дефисы удаляются. Имена нормализуются по
регистру, пробелам и ё/е. Основным считается первый пригодный номер в данных CRM,
затем первый пригодный email. Совпадение второстепенного номера не достаточно
для автоматического объединения. Изменение основного номера может создать
другой контакт; ручное объединение и привязка к адресату мессенджера — следующий
этап. История сообщений при этом не переносится и не удаляется автоматически.

Повторная синхронизация сохраняет ID при неизменной идентичности. Для детей
сохраняются прежние связи с исходными customer ID, в том числе при исчезновении
одной из дублирующих карточек. Противоречивые данные отмечаются для проверки.
Ручные связи ребёнок–контакт не удаляются импортом; устаревшие связи, созданные
импортом, обновляются. Канонические контакты и дети не удаляются физически.

## Статусы и интерфейс

Клиент — зелёный кружок, лид — голубой, архивный — красный. Если у контакта
несколько детей/карточек с разными статусами, приоритет: клиент, лид, архивный.
Фильтр статуса выбирает контакт, у которого есть хотя бы одна подходящая карточка.
Фильтр филиала сужает детей, группы и агрегированный статус до выбранного филиала.
Архив определяется явным removed=2; цвет не зависит от названия статуса обучения.

Слева один контакт, ФИО детей и статус. Перечень всех филиалов не дублируется.
Имя и подпись выбирают контакт внутри сервиса. Только кружок открывает выбор
CRM-карточки; ссылки в нём показывают ребёнка и филиал. Справа — родитель,
контактные данные, дети и актуальные группы. Это справочник, поле отправки
сообщений появится после реализации и проверки транспорта мессенджера.

Ширина левого блока по умолчанию 450 px при достаточной ширине окна. Разделитель
перетаскивается мышью; также поддерживает стрелки, Home/End с клавиатуры.
Минимальная ширина списка 300 px, максимальная 640 px с сохранением места справа.
На телефоне список и сведения переключаются; есть возврат к списку.

Поиск по родителю, ребёнку, телефону и email работает по индексу PostgreSQL.
Первые 30 контактов выдаются одной страницей; «Показать ещё» получает следующую.
Просмотр/поиск не обращается в CRM. Последние 60 открытых контактов кэшируются
в памяти вкладки; при новой опубликованной копии кэш сбрасывается. Персональные
данные не сохраняются в localStorage. Смена центра/выход очищает интерфейс и кэш.

## Надёжность и границы

Новая копия публикуется только после полного завершения всех этапов одной
транзакцией. До этого доступна прежняя полная копия. Ошибка/отмена сохраняют её.
Повтор страницы не создаёт дублей. Держатся текущая и предыдущая исходные копии;
старые исходные строки очищаются, канонические сущности и история остаются.

Ограничения первой версии: до 50 000 карточек с учётом филиалов за загрузку;
до 100 000 записей/1000 страниц одного списка; 500 записей на страницу. Превышение
даёт явную ошибку и сохраняет старую копию. Сведения одного контакта ограничены
1000 исходными карточками и 5000 связями групп, с явным признаком частичной выдачи.
Нагрузка первичной загрузки зависит от числа филиалов, групп и ограничений CRM;
фиксированное время не обещается. Периодическое обновление пока полное, не delta.

RLS отделяет организации, worker повторно проверяет актуальные права инициатора
и версию подключения перед записью страницы. Справочник пока доступен только
владельцу и администратору. Доступ операторов/руководителей требует отдельного
ACL филиалов и каналов. Нет открытой выдачи клиентских данных по общему токену.

Автодеплой перед миграцией делает локальный pg_dump и проверяет его оглавление.
Внешняя копия и полноценная проверка восстановления на пилоте ещё не подтверждены.
Ключ шифрования подключений хранится отдельно от дампов базы.

## Проверка

Тесты проверяют реальные миграции PostgreSQL, RLS, API и Chromium, а ответы
АльфаCRM заменены вымышленными данными по опубликованному контракту. Проверяются
несколько филиалов, дети одного родителя, несовпадения ФИО, нормализация телефонов,
повторная загрузка, возобновление после перезапуска, отмена в момент запроса,
смена ключа, отзыв роли, истёкшие/будущие группы, сохранение старой копии при сбое,
поиск без HTTP к CRM, выбор карточки и мобильный интерфейс.

Первое чтение реальных клиентов, статусов и CGI из CRM «Развивайся» ещё должно
быть подтверждено после нажатия «Загрузить из CRM» в установленной версии.
Успешная проверка филиалов в 0.3.0 этого не доказывает. Кнопка не отправляет
сообщения клиентам и не изменяет данные в АльфаCRM.
